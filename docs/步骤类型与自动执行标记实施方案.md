# 步骤类型与自动执行标记实施方案

## 1. 目标

本方案是“自动化深度与半自动工作流方案”的第一阶段落地文档，目标只有两件事：

- 为模板步骤引入明确的步骤类型
- 为步骤引入自动执行标记

这一步不直接实现完整的半自动批量执行，而是先把自动化需要的控制语义补到数据结构和界面层。只有这层明确后，后面的批量文本生成、人工断点和流程暂停才有稳定基础。

## 2. 设计原则

### 2.1 先补语义，不先补复杂调度

当前最缺的不是“更多执行按钮”，而是步骤到底属于哪类、是否允许自动跑、遇到什么情况必须停下。这些如果不先定义，后续自动化会一直停留在零散功能层。

### 2.2 自动化默认保守

第一版不应该默认把所有有模型引用的步骤都视为可自动执行。自动化必须是用户明确允许的行为，而不是系统擅自推断。

### 2.3 不破坏现有人工流程

新增步骤类型和自动执行标记后，当前：

- 手动编辑模板
- 手动执行单步
- 手动复制最终提示词

这些现有行为都必须保持不回归。

## 3. 步骤类型定义

第一版建议引入 3 类步骤。

### 3.1 `text_generation`

含义：

- 这是语言模型执行的文本生成步骤
- 主要产出中间文本资产
- 后续可参与半自动批量文本生成

典型用途：

- 生成图片描述
- 扩写风格提示
- 提炼镜头语言
- 生成中间说明文本

### 3.2 `manual`

含义：

- 这是人工确认或人工编辑步骤
- 系统不能自动跨过
- 即使绑定模型，也默认不作为自动执行步骤

典型用途：

- 人工二次改写
- 人工审阅
- 人工筛选结果

### 3.3 `external`

含义：

- 这是当前应用外部执行步骤
- 当前阶段只负责生成最终提示词，不负责真正调用图像/视频模型

典型用途：

- 复制提示词到外部生图工具
- 复制提示词到外部生视频工具

未来若应用正式接入生图/生视频模型，这一类步骤才有可能演进成内部可执行步骤。

## 4. 自动执行标记定义

在步骤类型之外，再引入一层显式控制：

```ts
autoRunEnabled?: boolean
```

含义：

- `true`：该步骤允许参与后续半自动流程
- `false` 或缺省：该步骤只允许手动执行

### 4.1 为什么还要单独有 `autoRunEnabled`

因为步骤类型和自动执行权限不是同一件事。

例如：

- 一个 `text_generation` 步骤，可能仍然希望先手动调试，不参与自动化
- 一个 `manual` 步骤，即使绑定了模型，也不应自动跳过

因此规则应拆成两层：

- 步骤类型决定“这一步属于什么角色”
- 自动执行标记决定“这一步是否允许进入自动化范围”

## 5. 建议字段结构

第一版建议把这两个字段落在 `TemplateStep` 上。

```ts
stepType?: 'text_generation' | 'manual' | 'external'
autoRunEnabled?: boolean
```

### 5.1 默认值策略

为了兼容旧模板，建议归一化规则如下：

- 缺失 `stepType` 时：
  - 如果步骤绑定了模型引用，则默认归一化为 `text_generation`
  - 否则归一化为 `manual`
- 缺失 `autoRunEnabled` 时：
  - 统一归一化为 `false`

这意味着：

- 旧模板不会直接突然进入自动化
- 用户必须明确开启自动执行

## 6. 与现有执行配置的关系

当前步骤已经有：

- 模型引用
- `temperature`
- `maxTokens`
- `systemPrompt`

新增的步骤类型和自动执行标记不替代这些字段，而是位于更上层。

关系如下：

- `execution.modelRefId`：决定步骤能否由模型执行
- `stepType`：决定步骤在工作流中的角色
- `autoRunEnabled`：决定步骤是否允许加入自动化

第一版推荐的判断逻辑：

- 手动单步执行：
  - 只看现有模型可执行性
- 后续半自动批量执行：
  - 只执行 `stepType === 'text_generation' && autoRunEnabled === true`

## 7. 模板编辑器 UI 方案

### 7.1 放置位置

建议把这组控制放到 `TemplateEditor` 的执行配置区里，因为它本质上属于步骤执行层。

### 7.2 展示方式

在每个步骤的执行配置摘要或展开区增加：

- 步骤类型选择器
- 自动执行开关

建议控件形式：

- 步骤类型：单选下拉或 segmented control
- 自动执行：开关或 checkbox

### 7.3 文案建议

步骤类型文案：

- `文本生成`
- `人工确认`
- `外部执行`

自动执行标记文案：

- `允许自动执行`

辅助说明：

- 文本生成：适合语言模型自动批量执行
- 人工确认：自动流程到这里必须停下
- 外部执行：当前只生成提示词，不自动调用图像/视频模型

### 7.4 联动规则

建议第一版做最小联动：

- 当步骤类型为 `manual` 或 `external` 时，`autoRunEnabled` 默认关闭
- 当步骤类型切到 `text_generation` 时，不自动替用户打开 `autoRunEnabled`
- 仍由用户明确打开

这样能避免误触发自动化。

## 8. 项目页展示建议

当前这一步不要求做完整自动化执行入口，但建议项目页能提前消费这层语义。

### 8.1 紧凑视图

紧凑模式只显示很弱的一层步骤角色提示，例如：

- `文本`
- `人工`
- `外部`

如果 `autoRunEnabled === true`，可以再加一个轻量标识：

- `自动`

### 8.2 详细视图

详细模式里可以明确显示：

- 步骤类型
- 是否允许自动执行
- 当前是否具备可执行模型条件

这一步先作为信息展示，为后面的自动化入口做铺垫。

## 9. 校验与限制

第一版建议加以下轻量约束：

### 9.1 `external` 步骤不应强制要求模型可执行

它的职责是生成最终提示词给外部工具，不一定需要本步骤自己执行模型。

### 9.2 `manual` 步骤允许绑定模型，但不参与自动化

这类步骤仍可保留手动单步执行入口，用于用户辅助生成和人工审阅结合的场景。

### 9.3 `text_generation` 不是自动执行的充分条件

还必须同时满足：

- `autoRunEnabled === true`
- 模型配置可用
- 依赖变量完整

## 10. 与未来半自动流程的衔接

这一步完成后，下一阶段“半自动批量文本生成”可以直接复用这些判断：

- 只扫描 `text_generation`
- 只执行 `autoRunEnabled === true`
- 遇到 `manual` 或 `external` 就停

也就是说，后续自动化不需要重新发明步骤语义，只要消费这里的结构即可。

## 11. 实施顺序

建议按以下顺序实现：

### 11.1 数据结构

- 在 `types.ts` 中扩展 `TemplateStep`
- 在 settings / schema / normalize 链路中兼容新字段

### 11.2 模板编辑器

- 在 `TemplateEditor` 执行配置区增加步骤类型与自动执行开关
- 在摘要区显示当前步骤角色

### 11.3 项目页消费

- `ProjectRunner` 详细模式显示步骤类型和自动执行标记
- 紧凑模式只做轻提示

### 11.4 预留自动化入口

- 暂不真正实现自动执行调度
- 只把语义层补齐

## 12. 验收标准

本方案完成后，应满足：

- 旧模板可正常打开，不报错
- 新旧模板保存后都能携带步骤类型和自动执行标记
- 用户可在模板编辑器中明确设置步骤类型
- 用户可显式开启或关闭“允许自动执行”
- 项目页能看到这层信息
- 当前单步手动执行行为不回归

## 13. 结论

自动化第一阶段不应该先做“大一键运行”，而应该先把：

- 这一步是什么
- 这一步能不能自动跑
- 这一步遇到时是否必须停下

这三件事定义清楚。

因此，本方案的价值不在于新增一个按钮，而在于为后续半自动工作流建立稳定的步骤语义基础。
