# 半自动批量文本生成实施方案

## 1. 目标

本方案是自动化第一阶段的真正执行层设计，目标是实现：

> 用户一次触发，系统批量执行一组“文本生成步骤”，自动回填步骤结果和输出变量，并在需要人工接管时暂停。

这一版明确是“半自动”，不是全自动工作流引擎。

## 2. 适用范围

### 2.1 解决的问题

当前用户在真实使用中会遇到：

- 一个模板里可能有数十到数百个文本生成步骤
- 这些步骤很多都只是为了生成中间描述类文本资产
- 用户不希望逐个点“生成”
- 但也不希望整个链条完全不可控

因此，第一版半自动能力主要解决：

- 文本步骤的一键批量执行
- 自动回填中间文本资产
- 自动同步输出变量
- 在需要用户判断或外部执行时停下来

### 2.2 暂不覆盖

这一版不覆盖：

- 图像模型执行
- 视频模型执行
- 外部工具自动调用
- 条件分支
- 自动重试策略编排
- 多项目并发工作流调度

## 3. 执行对象

只有同时满足以下条件的步骤，才允许进入半自动批量文本生成：

- `stepType === 'text_generation'`
- `autoRunEnabled === true`
- 当前步骤模型可执行
- 当前步骤依赖变量完整

换句话说：

- `manual` 步骤绝不自动跑
- `external` 步骤绝不自动跑
- 没开自动执行标记的文本步骤也不自动跑

## 4. 第一版执行入口

第一版建议只做一个入口：

## 4.1 批量执行选中步骤

用户先在模板或项目页中选择一批步骤，然后点击：

- `批量生成文本`

这一版不先做：

- 从当前步骤自动推进到下一个断点
- 基于依赖图全自动扫描所有可执行步骤

这样范围最稳，用户也更容易理解。

## 5. 执行前检查

批量执行启动前，系统应对选中步骤逐个做静态检查，并分成两类：

### 5.1 可执行项

满足所有条件，可以直接进入执行队列。

### 5.2 阻塞项

存在以下任一问题时，不能进入执行队列：

- 缺少变量
- 模型引用缺失
- 模型目录项缺失或被禁用
- provider 缺失或被禁用
- API Key 缺失
- 步骤类型不是 `text_generation`
- `autoRunEnabled !== true`

### 5.3 启动前反馈

在真正执行前，UI 应先给出一次汇总：

- 共选中多少步
- 其中多少步可执行
- 多少步被跳过
- 每类跳过原因是什么

用户确认后，再正式开始执行。

## 6. 执行顺序

第一版建议严格按当前步骤顺序串行执行，不做并发。

原因：

- 步骤之间存在变量依赖
- 串行更容易理解和调试
- 一旦失败，更容易停在明确位置

执行顺序以当前模板步骤顺序为准，选中集内按步骤在模板中的顺序执行。

## 7. 执行行为

对每个进入队列的步骤，执行行为与当前单步生成保持一致：

- 调用语言模型
- 用返回结果覆盖当前步骤结果
- 更新 `stepOutputMeta.updatedAt`
- 写入运行日志
- 同步输出变量

这意味着第一版不需要重新造一套执行链，只需要复用现有单步执行能力。

## 8. 暂停与停止规则

第一版半自动流程应在以下情况暂停：

### 8.1 执行失败

例如：

- 请求失败
- 模型返回错误
- 网络异常

建议默认行为：

- 当前步骤记为失败
- 流程整体暂停
- 用户决定是继续、跳过还是停止

### 8.2 依赖缺失

如果某步在运行前发现缺变量，应直接暂停，不应继续盲跑后续。

### 8.3 命中非自动步骤

如果选中集里包含：

- `manual`
- `external`

建议第一版直接在执行前排除并提示，不进入运行态。

### 8.4 用户主动停止

执行过程中应提供：

- `停止执行`

点击后：

- 当前请求不强杀
- 当前步完成后停止后续队列

第一版不要求做“中断当前 HTTP 请求”。

## 9. 结果处理

每个成功步骤完成后，应自动完成以下动作：

- 步骤结果回填
- 输出变量同步
- 运行日志写入
- 步骤状态刷新

这正是它比“逐个点击生成”更有价值的地方：不是只帮你点按钮，而是把中间文本资产链完整更新。

## 10. UI 方案

## 10.1 入口位置

建议在项目页提供半自动批量文本生成入口，因为它本质上是“项目运行行为”，不是模板结构编辑行为。

入口可放在：

- 项目页顶部工具区
- 或步骤列表顶部批量操作区

建议文案：

- `批量生成文本`

## 10.2 选择方式

第一版支持：

- 手动勾选步骤
- 只允许勾选 `text_generation` 步骤

后续可扩展：

- 全选可自动文本步骤
- 按模型引用筛选
- 按步骤类型筛选

## 10.3 执行前面板

点击入口后先出现确认面板，展示：

- 可执行步骤数
- 跳过步骤数
- 跳过原因列表
- 执行顺序预览

按钮：

- `开始执行`
- `取消`

## 10.4 执行中面板

执行时显示：

- 当前步骤名
- 当前进度 `x / n`
- 已成功数
- 已失败数
- 停止按钮

## 10.5 执行后面板

完成或暂停后显示：

- 成功项列表
- 失败项列表
- 跳过项列表

建议动作：

- `重跑失败项`
- `关闭`

## 11. 数据结构建议

第一版尽量少改持久化结构。

### 11.1 不新增复杂项目结构

执行中的批量状态建议先放在运行态 state，而不是持久化到项目。

例如：

```ts
batchTextRunState: {
  isRunning: boolean
  queueStepIds: string[]
  currentStepId?: string
  completedStepIds: string[]
  failedStepIds: string[]
  skippedStepIds: string[]
  stopRequested: boolean
}
```

这部分可以只存在前端内存态。

### 11.2 复用已有日志和结果结构

不新增新的单步结果存储结构，继续复用：

- `project.stepOutputs`
- `project.stepOutputMeta`
- `project.stepRunLogs`
- `project.variables`

## 12. 与人工流程的关系

这一版的关键，不是替代人工，而是减少人工重复。

因此仍然保留：

- 用户手动选择执行范围
- 用户手动停止
- 用户对失败项做判断
- 用户继续手动复制最终提示词到外部生图/生视频工具

自动化只接管：

- 中间文本资产的批量生成
- 结果回填
- 变量同步

## 13. 推荐实施顺序

### 第一阶段

- 在项目页加“批量生成文本”入口
- 接入步骤勾选和可执行性筛选
- 复用现有单步执行链做串行批量执行

### 第二阶段

- 补执行前检查面板
- 补执行中进度与停止能力
- 补失败项汇总

### 第三阶段

- 补“重跑失败项”
- 补“全选自动文本步骤”
- 补按模型引用筛选

## 14. 验收标准

本方案完成后，应满足：

- 用户可以选中一批文本生成步骤
- 系统能识别哪些步骤可自动执行、哪些不能
- 可执行步骤能串行批量运行
- 成功结果会自动回填并同步输出变量
- 失败会暂停并给出明确反馈
- 不会错误执行 `manual` 或 `external` 步骤
- 现有单步生成逻辑不回归

## 15. 结论

半自动批量文本生成是当前阶段最符合产品方向的自动化能力，因为它能显著降低“中间文本资产生产”的人工重复，同时又不会越过人工控制边界。

这一步做完后，产品会真正从“逐步手点的提示词工作台”进入“受控的半自动文本生产台”。
