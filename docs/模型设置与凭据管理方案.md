# PromptWordSplicer 模型设置与凭据管理方案

## 背景

当前项目已经具备：

- 模板级模型引用
- 步骤级模型引用选择
- 项目级步骤输出和变量沉淀

但模型来源仍然是代码内的静态预设列表，还没有真正的用户设置层。因此目前存在三个问题：

1. 用户不能自己维护可选模型列表。
2. 用户不能配置 API Key、Base URL 等连接信息。
3. 模板里的模型引用还不能脱离代码常量独立存在。

## 目标

本轮方案的目标不是立刻接入真实调用，而是先把“模型配置”这层抽象稳定下来，让后续接 `OpenAI / Anthropic / Gemini / OpenAI-Compatible` 时不再反复改结构。

具体目标：

1. 让设置页可以管理提供商配置。
2. 让设置页可以管理用户自己的模型目录。
3. 让模板里的模型引用指向“模型目录项”，而不是代码常量。
4. 凭据不进入模板，不进入项目，不进入项目备份。

## 总体设计

建议把模型相关配置拆成三层：

### 1. 提供商配置层

负责“怎么连到服务”。

例如：

- OpenAI 主账号
- Anthropic 主账号
- Gemini 主账号
- OpenAI-Compatible 私有网关

这一层保存：

- 提供商类型
- API Key
- Base URL
- 启用状态

### 2. 模型目录层

负责“有哪些模型可供模板选择”。

例如：

- 文案生成 GPT-4.1
- 长文整理 Claude 3.7 Sonnet
- 图片理解 Gemini 2.5 Pro

这一层保存：

- 显示名称
- 绑定哪个提供商配置
- 实际模型名
- 启用状态

### 3. 模板模型引用层

负责“模板内部怎么复用模型”。

例如：

- 生成描述用模型A
- 图片生成用模型

这一层只保存：

- 引用名称
- 指向哪个模型目录项

模板只关心“引用哪个模型”，不关心 API Key、Base URL 或服务商细节。

## 数据结构建议

### 提供商配置

```ts
interface ProviderConfig {
  id: string;
  label: string;
  providerType: 'openai' | 'anthropic' | 'gemini' | 'openai_compatible';
  apiKey: string;
  baseUrl?: string;
  enabled: boolean;
}
```

字段含义：

- `label`: 用户自定义显示名，例如“OpenAI 主账号”
- `providerType`: 协议类别
- `apiKey`: 凭据
- `baseUrl`: 对 OpenAI-Compatible 或自定义网关尤其重要
- `enabled`: 是否可用

### 模型目录项

```ts
interface ModelCatalogItem {
  id: string;
  label: string;
  providerConfigId: string;
  modelName: string;
  enabled: boolean;
}
```

字段含义：

- `label`: 用户看到的模型名称，例如“文案生成 GPT-4.1”
- `providerConfigId`: 关联到哪条提供商配置
- `modelName`: 真正发请求时传给 API 的模型名
- `enabled`: 是否允许模板继续引用

### 模板模型引用

建议把当前模板里的：

```ts
interface TemplateModelRef {
  id: string;
  label: string;
  presetId: string;
}
```

改成：

```ts
interface TemplateModelRef {
  id: string;
  label: string;
  modelCatalogItemId?: string;
}
```

含义变化：

- 不再指向代码常量里的模型预设
- 改为指向设置页里真正由用户维护的模型目录项
- 为空表示该引用尚未绑定模型

## 设置页改造方案

建议把设置页拆成两个主要区块。

### A. 提供商配置

每条配置展示为一张卡片，字段包括：

- 配置名称
- 提供商类型
- API Key
- Base URL
- 启用开关
- 删除按钮

建议行为：

- API Key 默认遮挡显示
- Base URL 仅对兼容接口或自定义网关开放填写
- 删除前要检查是否仍有模型目录项依赖这条配置

### B. 模型目录

每条模型展示为一张卡片，字段包括：

- 模型显示名
- 绑定的提供商配置
- 实际模型名
- 启用开关
- 删除按钮

建议行为：

- 只能从“已启用的提供商配置”中选择
- 删除前要检查是否仍有模板模型引用依赖这条模型目录项

## 模板编辑器改造方案

当前模板编辑器里的“模型引用”区已经存在，但引用的是静态预设模型。

下一步应改为：

- 模板级模型引用仍然保留
- 每个引用改为选择“模型目录项”
- 不再直接读取 `constants.ts` 里的预设模型列表

步骤级仍然只选择模型引用，不直接选 provider/model。

## 存储策略建议

### 第一版

为尽快可用，第一版可以继续走本地设置存储，但要明确隔离：

- 提供商配置和模型目录进入 settings
- 模板和项目数据不携带凭据
- 项目备份不导出凭据

### 后续增强

如果后面继续加强安全性，可以再把 `apiKey` 迁移到：

- Tauri 安全存储
- 系统钥匙串
- 或单独加密文件

但这不应阻塞第一版落地。

## 交互规则建议

1. 如果某个模型目录项被禁用：
   模板编辑器里仍可显示已有绑定，但要提示“当前模型已禁用”。

2. 如果某条提供商配置被禁用：
   依赖它的模型目录项应视为不可执行。

3. 如果模板引用绑定的模型目录项被删除：
   该引用自动变为空，并在模板编辑器中提示重新选择。

4. API Key 为空时：
   配置可以保存，但应标记为“未完成”，后续不能执行测试连接和真实调用。

## 实施顺序

建议按以下顺序实现：

1. 扩展 `settings` 数据结构，新增提供商配置和模型目录
2. 改设置页 UI，加入这两块编辑界面
3. 模板模型引用从静态预设切换为模型目录项
4. 迁移旧数据：静态预设模型引用在首次加载时尝试映射到模型目录
5. 后续再接测试连接和单步模型调用

## 非目标

本方案不包含：

- 真实 API 调用实现
- API 连通性测试
- 多用户同步
- 云端凭据管理

## 结论

下一阶段最合理的方向不是继续在步骤里堆模型字段，而是把“模型设置”正式提升为设置页能力。

推荐原则：

- 模板只引用模型
- 设置页维护模型
- 凭据只存在设置层
- 项目和模板不携带敏感信息
