# 自动化深度与半自动工作流方案

## 1. 背景

当前应用已经具备以下基础能力：

- 模板、项目、步骤的分层结构
- 语言模型提供的单步文本生成
- 输出变量在后续步骤中的引用
- 批量实例化、批量执行、运行日志与结果回填

但从真实使用场景看，产品仍然停留在“可手工操作”的层面，自动化深度不够：

- 当模板中存在大量“生成描述”“扩写说明”“整理风格词”之类步骤时，用户仍然要逐步触发
- 步骤之间虽然已经有变量引用关系，但还没有形成受控的半自动推进链
- 当前应用只接入语言模型，没有接入生图/生视频模型，因此后半段仍依赖用户复制最终提示词到外部工具

因此，自动化建设的重点不应是直接追求全自动，而应先把“中间文本资产生成”做成可控、可批量、可暂停的半自动工作流。

## 2. 产品定位

本应用当前阶段的定位不是通用聊天工具，也不是完整的文生图平台，而是：

> 面向图像/视频内容生产流程的分步 AI 工作台，先自动化中间文本资产生成，再逐步接入生图/生视频执行。

这一定位意味着：

- 语言模型当前主要负责生成中间文本资产
- 输出变量是流程中的核心资产，不只是临时文本
- 最终提示词仍可能需要复制到外部工具执行
- 自动化必须保留人工接管能力

## 3. 自动化分级

### 3.1 A 级：人工驱动，AI 辅助

这是当前应用已经具备的基础档位。

特征：

- 用户手动填写输入变量
- 用户手动选择步骤并执行
- AI 生成中间文本资产
- 用户手动复制最终提示词到外部工具

适用：

- 小规模模板
- 需要频繁人工修改中间结果
- 还在探索模板结构

问题：

- 步骤一多时效率急剧下降
- 同类文本步骤不能批量跑
- 人工重复操作很多

### 3.2 B 级：半自动批量文本生成

这是下一阶段最应该进入的自动化层。

特征：

- 只自动执行“文本生成类步骤”
- 用户一次触发，系统批量执行多步语言模型任务
- 输出结果自动写入步骤结果与输出变量
- 遇到断点条件时暂停，交还用户

适用：

- 同一模板中存在大量描述生成步骤
- 用户想自动完成前半段文本资产生产
- 后半段仍保留人工复制到外部生图/生视频工具

这是本方案主推的第一版自动化目标。

### 3.3 C 级：按依赖顺序的半自动流程推进

在 B 级稳定后，可以进入这一层。

特征：

- 用户从某一步开始触发
- 系统按依赖顺序自动推进
- 只执行允许自动化的步骤
- 命中人工断点或外部步骤时停下

适用：

- 模板步骤量大
- 存在明显的前后依赖链
- 用户希望系统自动判断下一步可执行项

### 3.4 D 级：全链路自动化

这是未来方向，不是当前阶段目标。

特征：

- 文本步骤自动执行
- 生图步骤自动调用图像模型
- 生视频步骤自动调用视频模型
- 自动保存和归档生成产物

前提：

- 文本链自动化已经稳定
- 生图/生视频模型已正式接入
- 错误治理、重试策略、人工断点机制成熟

## 4. 当前阶段的目标

当前阶段只建议推进到 **B 级：半自动批量文本生成**。

理由：

- 它最贴合当前“先用语言模型生成中间描述，再交给外部生图工具”的实际流程
- 它能显著减少用户面对数百个描述生成步骤时的重复点击
- 它不会过早引入“全自动错了也一路跑下去”的风险
- 它为未来生图/生视频接入保留了清晰的扩展面

## 5. 步骤类型建议

为支持自动化深度控制，后续建议显式区分步骤类型。

### 5.1 文本生成步骤

定义：

- 绑定语言模型
- 允许自动执行
- 主要产出中间文本资产

典型场景：

- 图片描述生成
- 风格词扩写
- 镜头语言整理
- 标签提炼
- 提示词润色

### 5.2 人工确认步骤

定义：

- 需要用户停下来查看、修改、筛选
- 系统不能自动跳过

典型场景：

- 人工二次改写
- 多结果中人工选优
- 结果审核与确认

### 5.3 外部执行步骤

定义：

- 当前应用内部不执行
- 需要用户复制结果到外部工具

典型场景：

- 复制到外部生图工具
- 复制到外部生视频工具
- 复制到第三方平台继续处理

未来接入生图/生视频模型后，这一类步骤可逐步被替换为“内部执行步骤”。

## 6. 人工断点设计

自动化不是越深越好，关键是明确何时必须停下。

第一版建议把以下情况统一视为人工断点：

- 命中人工确认步骤
- 命中外部执行步骤
- 缺少变量
- 模型不可用
- API Key 缺失
- 单步执行失败
- 用户主动中止

停下后系统应该给出明确提示：

- 停在了哪一步
- 为什么停
- 是缺变量、缺模型、失败还是命中了人工断点
- 下一步用户该怎么处理

## 7. 第一版半自动工作流范围

### 7.1 范围内

第一版只做以下范围：

- 只自动执行文本生成步骤
- 用户手动选择一个执行范围
- 系统批量执行这批文本生成步骤
- 自动写入步骤结果
- 自动同步输出变量
- 遇到人工断点或错误就停下
- 给出执行进度和失败列表

### 7.2 暂不做

第一版明确不做：

- 自动执行外部生图/生视频步骤
- 自动跨越人工确认步骤
- 自动根据自然语言自主决策下一步
- 自动重试所有失败项
- 条件分支编排
- 多步骤并发调度优化

## 8. 执行入口建议

第一版可以提供两类入口。

### 8.1 批量执行选中步骤

用户先选中一批文本步骤，再点击：

- 批量执行选中步骤

优点：

- 简单直接
- 用户掌控感强
- 易于理解

缺点：

- 需要用户自己理解流程依赖

### 8.2 从当前步骤执行到下一个断点

用户在某个步骤点击：

- 从这里开始自动执行

系统行为：

- 从当前步骤开始
- 只向后执行允许自动化的文本步骤
- 遇到断点就停

优点：

- 更接近真实工作流
- 适合长流程模板

缺点：

- 依赖判断和暂停说明要更清晰

建议：

第一版优先做 `批量执行选中步骤`，第二版再加 `从当前步骤执行到下一个断点`。

## 9. 数据结构建议

当前暂不需要重写底层数据结构，但建议为自动化控制预留字段。

### 9.1 步骤执行模式

可在步骤层增加类似字段：

```ts
runMode: 'manual' | 'text_auto' | 'external'
```

含义：

- `manual`：人工步骤
- `text_auto`：可自动执行的文本步骤
- `external`：外部执行步骤

### 9.2 断点标记

可额外增加：

```ts
isManualCheckpoint?: boolean
```

用于在自动推进时强制停下。

### 9.3 执行结果状态

项目运行态层面可增加：

```ts
automationStatus?: 'idle' | 'running' | 'paused' | 'failed' | 'completed'
pauseReason?: 'manual_checkpoint' | 'missing_variable' | 'execution_error' | 'external_step'
```

第一版不要求持久化到项目结构中，也可以先保存在运行态。

## 10. UI 方案建议

### 10.1 步骤层

步骤卡片可新增或强化以下信息：

- 当前步骤类型
- 是否允许自动执行
- 是否是人工断点
- 如果被上游结果影响，提示“引用变量已更新”

### 10.2 模板层

模板编辑器需要逐步支持：

- 标记步骤类型
- 标记是否允许自动执行
- 标记人工断点

### 10.3 项目层

项目页需要新增：

- 批量文本执行入口
- 自动化进度
- 暂停原因
- 失败列表
- 继续执行 / 跳过 / 终止

## 11. 推荐实施顺序

建议按以下顺序推进：

### 第一阶段

- 引入步骤类型
- 引入“允许自动执行”标记
- 支持批量执行选中步骤

### 第二阶段

- 引入人工断点
- 支持“从当前步骤执行到下一个断点”
- 加强暂停原因提示

### 第三阶段

- 优化失败重跑策略
- 增加自动执行前检查面板
- 增加按依赖排序的执行辅助

### 第四阶段

- 接入内部生图步骤
- 接入内部生视频步骤
- 演进到更深的半自动或全链路自动化

## 12. 结论

当前最合理的自动化方向不是全自动，而是：

> 先把前半段文本资产生成做成受控的半自动流程，后半段继续保留人工接管。

这个方向既符合当前实际使用方式，也为未来接入生图/生视频模型保留了清晰的演进路径。

下一步如果继续推进自动化，建议先落一份更具体的实施方案：

- 步骤类型与自动执行标记实施方案
- 半自动批量文本生成实施方案
