# TemplateEditor 清理与统一实施方案

## 背景

当前 `TemplateEditor` 已经承担了大量核心能力：

- 模板基础信息编辑
- 步骤内容编辑
- 模型引用配置
- 执行配置模板应用
- 批量复制 / 批量套用执行配置
- 输出到变量配置
- 变量自动补全

能力已经够多，但也带来了明显问题：

- 信息密度不稳定
- 主次操作混杂
- 术语和文案不完全统一
- 历史编码污染和旧文案残留
- 某些区域更像“设置面板堆叠”，而不是高频编辑器

因此这一轮不新增大功能，目标是把 `TemplateEditor` 收成一个更稳定、更易维护、更符合高频编辑使用场景的编辑器。

## 目标

### 产品目标

- 让模板编辑区更像“编辑器”，而不是“配置项堆叠页”
- 提高信息密度，但不牺牲理解成本
- 强化高频动作，收纳低频动作
- 统一术语，减少用户心智切换

### 工程目标

- 清理历史坏编码文案
- 统一 `TemplateEditor` 内部局部状态和交互层级
- 让后续继续扩展结构化输出、输出拆变量时不至于再失控

## 范围

本轮只处理 `TemplateEditor` 相关问题，不扩展到：

- `ProjectRunner`
- `Sidebar`
- 设置页
- 批量执行链
- 结构化输出正式落地

但会为后续这些能力留出更稳定的承载结构。

## 核心问题清单

### 1. 术语不统一

当前与模板编辑相关的概念有：

- 模型引用
- 执行模板
- 输出到变量
- 步骤结果
- 步骤执行配置
- 提示词
- 同步模板

这些词已经比最早版本清晰，但还没有完全统一，尤其在提示文案、按钮和说明文案之间，存在不同叫法并存的问题。

### 2. 执行配置区层级过重

当前执行配置区承载了：

- 模型引用
- 参数
- system prompt
- 执行模板应用
- 保存为模板
- 复制执行配置
- 批量应用已复制配置

这些都放在一个区域里，导致：

- 主操作不突出
- 次级操作抢占视觉
- 配置区高度过大

### 3. 输出到变量区不够紧凑

这块虽然已经比旧版本合理，但还可以继续优化：

- 变量 key 信息仍然偏“配置语义”
- 说明文案还不够产品化
- 是否绑定、绑定到哪里、后续有什么影响，这三层信息应该更清楚地分层

### 4. 步骤头部与步骤正文的职责还不够清晰

步骤头部目前承担了：

- 步骤名称
- 删除
- 复制执行配置
- 批量选择
- 已复制标记

步骤正文又承担：

- 提示词编辑
- 执行配置
- 输出变量

但“什么应该放头部、什么应该放正文、什么该收进次级操作”还没有完全收干净。

### 5. 旧编码与坏文案残留

这是持续性风险：

- 某些中文文案已经混入历史坏编码
- 某些说明文案不再符合当前产品逻辑
- 后续如果继续在脏文案上改，会再次引发维护问题

## 设计原则

### 1. 编辑优先

用户进入 `TemplateEditor` 的首要任务是：

- 写提示词
- 改步骤
- 配执行配置

不是阅读大段说明，不是处理一堆边角按钮。

### 2. 主次分层

- 一级：当前步骤最常用的编辑行为
- 二级：执行配置和输出变量配置
- 三级：复制、批量、保存为模板等辅助能力

### 3. 紧凑但不隐藏关键逻辑

不是一味压高度，而是：

- 高频信息常驻
- 低频信息折叠
- 辅助说明弱化

### 4. 先统一，再扩展

这轮不急着加“结构化输出 UI”，而是先把 `TemplateEditor` 变成一个足够稳的容器，便于后续继续加能力。

## 实施内容

## 第一部分：术语和文案统一

### 目标

统一所有与 `TemplateEditor` 直接相关的显示术语，清理坏编码。

### 处理对象

- 区块标题
- 按钮文案
- 状态文案
- 提示文案
- 空态文案

### 推荐统一结果

- `提示词`
- `模型引用`
- `执行模板`
- `输出到变量`
- `复制配置`
- `应用配置`
- `保存为模板`
- `批量应用`
- `同步模板`
- `编辑原文`

### 验收标准

- `TemplateEditor` 页面内不再出现乱码文案
- 同一概念在不同位置不再使用不同叫法

## 第二部分：步骤头部瘦身

### 目标

让步骤头部只承担“导航和轻操作”，不要抢正文空间。

### 调整方案

保留在头部的内容：

- 步骤序号
- 步骤名称
- 选中状态
- 已复制配置标记
- 删除按钮

收纳或弱化的内容：

- 复制执行配置
- 应用已复制配置
- 批量选择相关操作

### 建议实现

- 头部只保留一颗 `更多` 按钮
- 复制配置、应用已复制配置放进该菜单
- 批量选择入口放在模板编辑器更上层，而不是每个步骤头部重复出现

### 验收标准

- 步骤头部横向视觉更稳定
- 单步步骤卡片首屏信息更清楚

## 第三部分：执行配置区重组

### 目标

让执行配置区从“堆字段”变成“可快速理解和修改”的结构。

### 新结构建议

#### A. 执行摘要条

常驻显示：

- 当前模型引用
- 当前执行模板（若有）
- `temperature`
- `maxTokens`

这部分用一条紧凑摘要展示，不直接铺开全部字段。

#### B. 执行配置展开区

展开后才显示：

- 模型引用选择
- 参数输入
- system prompt
- 应用执行模板
- 保存当前配置为模板

#### C. 次级操作区

放：

- 复制执行配置
- 应用已复制配置

### 验收标准

- 用户不展开也能看懂当前步骤大致执行配置
- 展开后仍然能完整修改
- 主次操作不再混在同一层

## 第四部分：输出到变量区重组

### 目标

让“输出到变量”更像结果流转配置，而不是技术字段配置。

### 调整方向

默认展示：

- 是否已绑定
- 当前变量 key

展开后再展示：

- 变量 key 输入
- 绑定说明
- 变量是否来自步骤输出

### 文案建议

避免技术味过强的说明，改成更直接的产品语言，例如：

- `未绑定输出变量`
- `当前输出将同步到 {{variable_key}}`

### 验收标准

- 用户可以快速判断这一步结果是否会进入后续变量流
- 变量配置区不再抢占正文高度

## 第五部分：步骤内容区优先级提升

### 目标

让提示词内容区始终成为步骤卡片的主视觉中心。

### 调整方案

- 提示词编辑区保持常驻
- 自动补全面板继续保留
- system prompt 不与主提示词正文抢主位置
- 局部改写、同步模板、还原等动作继续存在，但视觉进一步收紧

### 验收标准

- 用户进入步骤后第一眼看到的是提示词编辑内容
- 不是先看到一堆配置和说明

## 第六部分：批量操作入口重构

### 目标

保留当前批量能力，但避免在每个步骤里重复占空间。

### 调整方案

将这些能力上提到模板级工具条：

- 全选步骤
- 清空选择
- 按模型引用筛选选择
- 批量应用已复制配置

单个步骤中只保留：

- 当前步骤复制配置

### 验收标准

- 步骤卡片更轻
- 批量操作仍然完整可用

## 实施顺序

建议按以下顺序推进：

1. 清理坏编码文案和术语
2. 收步骤头部
3. 重组执行配置区
4. 重组输出到变量区
5. 上提批量操作入口
6. 统一收尾和回归检查

## 风险

### 1. 误伤现有功能

`TemplateEditor` 当前承载功能多，重组时容易误伤：

- 执行模板应用
- 保存为模板
- 变量自动补全
- 批量应用配置

因此这一轮必须坚持“小步重排，不顺手重写业务逻辑”。

### 2. 编码污染二次扩散

仓库已有旧编码残留，如果在脏文本基础上继续替换，容易再次打坏 JSX 结构。

因此建议：

- 每次只改一个区域
- 每步都跑定向类型检查

## 验收标准

完成后至少满足：

- `TemplateEditor` 页面内可见乱码清理完成
- 术语统一
- 步骤头部更轻
- 执行配置区有摘要层和展开层
- 输出到变量区更清晰
- 批量操作不再在每个步骤里重复占空间
- 不影响当前模板保存、执行模板应用、变量自动补全、复制配置与批量应用逻辑

## 测试计划

至少完成以下检查：

- 打开已有模板，步骤列表正常显示
- 编辑提示词内容，自动补全正常
- 修改执行配置，保存模板正常
- 应用执行模板后参数正常覆盖
- 保存当前配置为模板正常
- 复制执行配置与批量应用已复制配置不回归
- 输出到变量配置保存正常
- `cmd /c node_modules\\.bin\\tsc.cmd --noEmit` 通过

## 结论

`TemplateEditor` 现在最需要的不是继续加功能，而是做一次“编辑器化”清理：

- 强化编辑主流程
- 弱化配置噪音
- 统一术语
- 清理历史包袱

这一步做完后，再继续推进“结构化输出与输出拆变量”，风险会低很多。
