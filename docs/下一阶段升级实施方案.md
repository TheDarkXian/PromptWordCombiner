# PromptWordSplicer 下一阶段升级实施方案

## 1. 目标

本方案用于指导 `PromptWordSplicer` 从“本地提示词拼接与单步 AI 执行工具”继续升级为“面向单人高频批量生产的本地 AI 工作台”。

本阶段不追求：

- 节点画布
- 多人协作
- 云同步
- Agent 自主编排

本阶段重点追求：

- 批量生产效率
- 变量与步骤关系的结构化
- 人工控制优先前提下的 AI 执行提效
- 模板资产的长期稳定沉淀

## 2. 产品判断

当前产品的核心用户仍然是“需要批量生成图像提示词、格式化文本、结构相近但变量略有差异内容的单人高频用户”。

因此，升级方向应遵循以下原则：

1. 先强化批量生产链路，不优先扩更多模型。
2. 先强化结构化变量和输出，不优先做复杂自动化。
3. 先让人工工作流更顺，再增加半自动执行能力。
4. 模板、模型、变量、运行记录都要可回看、可复用、可导出。

## 3. 总体路线

下一阶段建议分为三条主线并行推进：

1. 执行配置模板库
2. 批量结果导出增强
3. 结构化输出与输出拆变量

它们的优先级顺序为：

1. 执行配置模板库
2. 批量结果导出增强
3. 结构化输出与输出拆变量
4. 变量自动补全与来源跳转
5. 模板版本快照

## 4. 方案一：执行配置模板库

### 4.1 目标

把当前“从某一步复制执行配置”的临时能力，升级为正式可管理的“执行配置模板库”。

用户应能保存一整套：

- 模型引用
- temperature
- maxTokens
- systemPrompt

并在不同模板、不同步骤中反复套用。

### 4.2 用户价值

- 不需要反复从旧步骤复制配置
- 常用 AI 工作风格可标准化沉淀
- 不同模板之间可以共享一套稳定执行策略

### 4.3 数据结构建议

在 `AppSettings` 中新增：

```ts
interface ExecutionPresetTemplate {
  id: string;
  label: string;
  description?: string;
  modelRefStrategy?: 'keep_current' | 'bind_specific_model_catalog_item';
  modelCatalogItemId?: string;
  temperature?: number;
  maxTokens?: number;
  systemPrompt?: string;
  enabled: boolean;
  createdAt: number;
  updatedAt: number;
}
```

说明：

- `modelRefStrategy = keep_current` 表示只覆盖参数和 system prompt，不强制覆盖当前步骤模型引用
- `bind_specific_model_catalog_item` 表示该模板本身绑定一个具体模型目录项

### 4.4 界面方案

建议新增两个入口：

1. 设置页
用于管理执行配置模板库：
- 新建
- 编辑
- 启用 / 禁用
- 删除

2. 模板编辑页
在步骤执行配置区新增：
- 应用执行模板
- 保存当前步骤为执行模板

### 4.5 实施步骤

1. 扩展 `AppSettings` 和存储归一化逻辑
2. 在设置页新增执行模板管理区
3. 在模板编辑器步骤区增加“应用模板 / 保存模板”入口
4. 保留原有“复制执行配置”能力作为轻量补充，不立即移除

### 4.6 验收标准

- 可以在设置页创建和编辑执行模板
- 可以从步骤快速应用执行模板
- 可以把当前步骤配置保存为模板
- 模板禁用后不再出现在默认可选列表

## 5. 方案二：批量结果导出增强

### 5.1 目标

把当前批量执行从“能跑完”升级为“跑完就能拿结果继续交付”。

### 5.2 当前问题

当前已支持：

- 批量实例化
- 批量执行某一步
- 成功 / 失败筛选
- 基础结果导出

但仍不足：

- 导出结构还不够贴近业务
- 不能方便导出指定步骤结果
- 不能把项目变量、模板信息、步骤输出组合成最终交付表

### 5.3 升级目标

支持按模板步骤导出：

- 项目名
- 模板名
- 批量执行步骤名
- 执行状态
- 错误信息
- 当前步骤结果
- 关键输入变量
- 关键局部变量
- 关键输出变量

支持导出格式：

- CSV
- JSON
- Markdown

### 5.4 数据组织建议

新增统一导出行结构：

```ts
interface BatchExportRow {
  projectId: string;
  projectName: string;
  templateId: string;
  templateName: string;
  stepId: string;
  stepName: string;
  status: 'success' | 'error' | 'skipped';
  error?: string;
  stepOutput?: string;
  inputVariables: Record<string, string>;
  localVariables: Record<string, string>;
  outputVariables: Record<string, string>;
}
```

### 5.5 界面方案

在批量执行结果面板中新增：

- 导出当前筛选结果
- 导出成功项
- 导出失败项
- 导出指定步骤结果
- 导出完整项目上下文

### 5.6 实施步骤

1. 抽出统一 `batchExportService`
2. 增加导出结构映射层
3. 增加导出格式选择
4. 在结果弹窗中加入导出入口

### 5.7 验收标准

- 能导出成功 / 失败筛选结果
- 能导出指定步骤结果
- 能导出包含变量信息的交付表
- CSV 与 JSON 字段稳定、格式一致

## 6. 方案三：结构化输出与输出拆变量

### 6.1 目标

让某一步不再只产生一整段自由文本，而是能产出结构化字段，并自动进入多个变量。

### 6.2 用户价值

- 降低后续步骤对自由文本解析的依赖
- 让批量导出更可控
- 让提示词、图像参数、标签、描述等字段稳定分离

### 6.3 能力拆分

分两阶段落地：

#### 第一阶段：结构化输出提示

模板步骤可配置期望字段，例如：

- title
- description
- style
- negative_prompt

这阶段先不强校验，只提供输出结构提示和辅助填充。

#### 第二阶段：输出拆变量

允许一个步骤绑定多个输出字段到多个变量，例如：

```ts
interface StepStructuredOutputBinding {
  field: string;
  variableKey: string;
  variableLabel?: string;
}
```

### 6.4 数据结构建议

在 `TemplateStep` 中扩展：

```ts
interface TemplateStep {
  ...
  structuredOutputFields?: {
    key: string;
    label: string;
    description?: string;
  }[];
  structuredOutputBindings?: StepStructuredOutputBinding[];
}
```

在 `Project` 中保留当前 `stepOutputs` 不变，同时增加结构化缓存：

```ts
stepStructuredOutputs?: Record<string, Record<string, string>>;
```

### 6.5 界面方案

模板编辑页：

- 配置“期望输出字段”
- 配置“字段 -> 变量”的映射关系

项目页：

- 当步骤配置了结构化输出字段时，结果区增加字段化编辑方式
- 支持整段结果与结构化字段双视图切换

### 6.6 实施步骤

1. 先加结构化输出字段配置
2. 再加字段到变量映射
3. 再加项目页结构化填写区
4. 最后再考虑 AI 输出自动解析

### 6.7 验收标准

- 模板能配置结构化输出字段
- 项目能保存字段化结果
- 字段结果能稳定进入多个变量
- 后续步骤能通过 `{{variable_key}}` 使用这些字段

## 7. 配套增强项

### 7.1 变量自动补全

目标：

- 在提示词输入中输入 `{{` 时展示变量候选
- 变量候选按来源分类：
  - 输入变量
  - 局部变量
  - 输出变量

### 7.2 变量来源跳转

目标：

- 点击变量引用可跳到来源步骤或定义位置
- 提高长模板维护效率

### 7.3 模板版本快照

目标：

- 每次保存模板时保留历史版本
- 支持查看和恢复历史快照

## 8. 开发顺序建议

建议按以下顺序推进：

### 阶段 A

- 执行配置模板库
- 变量自动补全

### 阶段 B

- 批量结果导出增强
- 变量来源跳转

### 阶段 C

- 结构化输出字段
- 输出拆变量

### 阶段 D

- 模板版本快照
- 结构化输出与批量导出联动

## 9. 风险与控制

### 9.1 复杂度风险

结构化输出和输出拆变量很容易把当前轻量数据模型做重。

控制办法：

- 先做辅助结构，不强依赖 AI 自动解析
- 先让用户能手动修订结构化结果

### 9.2 兼容性风险

现有项目和模板已经有较多历史数据。

控制办法：

- 所有新增字段都必须可选
- 所有加载路径都必须走 normalize
- 不直接破坏旧 `stepOutputs` 逻辑

### 9.3 认知负担风险

如果一次性暴露太多“结构化输出”“模板库”“变量映射”概念，用户会觉得复杂。

控制办法：

- 默认仍保持当前简洁工作流
- 高级能力放在详细区或二级入口

## 10. 验收口径

本阶段完成后，应达到以下状态：

1. 用户能快速复用一套执行配置，而不是重复复制旧步骤
2. 用户能把批量执行结果直接导出为可交付数据
3. 用户能让一个步骤稳定产出多个结构化字段并进入多个变量
4. 用户能更快地在模板中引用和追踪变量
5. 模板资产具备初步版本可回退能力

## 11. 最终建议

如果只允许先做一项，优先做：

1. 执行配置模板库

如果允许连续做两项，建议做：

1. 执行配置模板库
2. 批量结果导出增强

如果允许做完整一轮升级，建议按本方案的 A -> B -> C -> D 四阶段推进。
