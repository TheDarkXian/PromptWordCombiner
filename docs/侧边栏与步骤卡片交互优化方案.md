# 侧边栏与步骤卡片交互优化方案

## 背景

当前应用已经具备：

- 项目级变量体系
- 单步生成
- 运行记录
- 紧凑 / 详细双视图

但在实际使用中，`Sidebar` 和 `ProjectRunner` 的信息密度、折叠策略和状态语义还没有完全对齐当前产品方向，已经开始影响高频使用体验。

本轮优化只聚焦交互收口，不改底层模型执行链和项目数据结构。

## 调查结论

### 1. 侧边栏结果变量区确实会被长文本撑坏

当前结果变量区实现位置：

- [Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:312)
- [Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:347)

现状：

- 每个结果变量都默认展示完整 `AutoResizeTextarea`
- `AutoResizeTextarea` 会按内容高度展开
- 结果变量一旦很长，会把后续变量整体向下顶走
- 用户即使只想确认变量名和来源，也必须先承受整段内容占位

判断：

- 这是结构问题，不是样式细节问题
- 结果变量默认不应展开正文，至少应支持单条折叠

### 2. 步骤结果文本框也缺少折叠层

当前步骤结果区实现位置：

- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:613)
- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:621)

现状：

- 步骤卡片展开后，结果框始终展示
- 结果一长，整张卡片高度会明显膨胀
- 当前没有“只看摘要 / 展开正文”的层级

判断：

- 这和“默认紧凑、按需详细”的方向冲突
- 步骤结果应该有独立折叠，不应强制常驻全文

### 3. 步骤结果区的自适应高度存在不稳定问题

当前 `ProjectRunner` 内部没有复用通用文本框，而是自带一份本地 `AutoResizeTextarea`：

- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:33)

现状：

- `Sidebar`、`TemplateEditor`、`PromptEditor` 已经走通用组件
- `ProjectRunner` 仍保留一份本地实现
- 步骤结果区还额外叠加了：
  - `min-h-[52px]`
  - 外层容器 padding
  - 文本框字体与行高配置

这会导致两个问题：

- 行高测量逻辑不一致
- 在多次编辑、恢复结果、长文本粘贴后，容易出现“高度比内容多出几行”的视觉偏差

判断：

- 这不是单纯的 CSS 微调问题
- 应优先统一到共享 `AutoResizeTextarea`
- 同时加折叠层，避免长文本始终依赖高度自适应

### 4. 运行记录现在仍然侵入紧凑视图

当前运行记录区实现位置：

- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:660)

现状：

- 只要存在 `latestLog`，紧凑模式也会显示运行记录摘要
- 这会让卡片在“已有运行历史”的项目里持续变高

判断：

- 这和你现在要的“紧凑干活视图”冲突
- 运行记录应完全收进 `详细视图`
- 紧凑模式只保留头部运行状态徽标即可

### 5. “依赖待更新”标签的语义已经和当前方向冲突

当前逻辑位置：

- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:195)
- [ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:421)

现状：

- `依赖待更新` 是通过 `getStepStatus(variable.sourceRef) === 'stale'` 推出来的
- `stale` 的定义仍然依赖 `step_output` 变量是否落后于 `stepOutputs`
- 但你当前希望的是“结果自动同步变量”，而不是继续强调“手动写入变量”

这里出现了语义错位：

- 如果步骤结果编辑后变量没有同步，才会出现 `stale`
- 但产品方向上你已经明确不希望用户理解“写入变量 / 更新变量”这套心智

判断：

- `依赖待更新` 不是完全没意义
- 但它现在依赖的是旧语义，容易误导
- 要么改成真正的“上游结果已变化”
- 要么先从紧凑视图撤掉

### 6. 侧边栏导入/导出按钮区确实又丑又占空间

当前按钮区位置：

- [Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:204)

现状：

- `导入变量表`
- `导出 JSON`
- `导出 CSV`

三颗按钮并排平铺，既占纵向，也占横向。

判断：

- 这是典型的“同类操作应该合并成一个动作组”
- 它们应该收成一个入口，例如：
  - `变量表`
  - 点击展开菜单
  - 菜单中再分 `导入 / 导出 JSON / 导出 CSV`

## 修改目标

本轮目标是把这几个区域重新分层：

1. 默认只看结构和状态
2. 长内容默认折叠
3. 运行记录只留在详细视图
4. 去掉和旧变量写入语义强绑定的状态噪音
5. 合并同类低频操作

## 具体修改方案

### A. 结果变量区改为“卡片摘要 + 单条展开”

#### 方案

每个结果变量卡片分两层：

1. 摘要头

- `{{variable_key}}`
- 显示名
- 来源步骤 / 来源类型
- 状态点
- `复制`
- `展开 / 收起`

2. 内容体

- 默认收起
- 展开后再显示变量正文

#### 交互规则

- 默认全部收起
- 只展开用户主动查看的条目
- 若变量内容为空，不展开正文，只显示空态

#### 额外建议

- 正文展开后仍然不要无限高度
- 设一个最大可见高度，例如 `max-h-[240px]`
- 超出部分滚动，不再继续顶开整个侧栏

### B. 步骤结果区改为“摘要折叠 + 正文展开”

#### 方案

在每个步骤结果区增加独立折叠状态：

1. 默认紧凑模式

- 只显示：
  - `步骤结果`
  - 已绑定变量 key
  - 一行摘要
  - `展开结果`

2. 展开后

- 才显示完整结果输入框
- 才显示 `清空`

#### 摘要规则

- 有内容时显示前 `1~2` 行或前 `N` 个字符
- 无内容时显示空态提示

#### 结果

- 紧凑模式下步骤卡片高度不再跟全文长度强绑定

### C. 统一步骤结果区到共享 AutoResizeTextarea

#### 方案

删除 `ProjectRunner` 内部本地 `AutoResizeTextarea`，统一复用：

- [components/common/AutoResizeTextarea.tsx](/E:/Project/Vscode/PromptWordSplicer/components/common/AutoResizeTextarea.tsx:1)

#### 原因

- 现在不同页面已经有两套高度计算逻辑
- 继续维护分叉只会让“n+x 行”问题反复出现

#### 实施细节

- `ProjectRunner` 引入共享组件
- 保留结果区视觉样式，但不再保留本地实现
- 展开态下仍可编辑
- 收起态只显示摘要，不参与高度计算

### D. 运行记录彻底移入详细视图

#### 方案

当前逻辑：

```tsx
(viewMode === 'detail' || runState === 'error' || latestLog)
```

要改成：

```tsx
viewMode === 'detail'
```

#### 紧凑模式保留内容

- 步骤头部运行状态徽标
- 若刚执行失败，可在头部保留一行短错误

#### 详细模式展示内容

- 运行记录区完整保留
- 历史展开
- 复制 prompt / 复制结果 / 恢复结果
- 清空步骤日志

这样可以保证：

- 干活时卡片短
- 排查时信息仍全

### E. “依赖待更新”标签处理方案

#### 当前问题

它的含义本质上还是：

- 某个上游步骤结果改了
- 但绑定变量没有同步

这套语义已经和当前“自动同步变量”方向冲突。

#### 建议处理

第一轮先做保守收口：

1. 从紧凑模式头部移除 `依赖待更新`
2. 详细模式里保留依赖详情
3. 标签文案暂时改成更中性的：
   - `上游结果已变化`
   - 或 `引用结果已变化`

#### 后续再决定

等变量同步策略彻底统一后，再决定：

- 完全删除这类状态
- 或保留真正有意义的“上游变化提醒”

### F. 侧边栏变量表操作合并为单一动作组

#### 方案

把三颗按钮收成一个 `变量表` 动作组：

1. 主按钮

- `变量表`
- 或 `导入/导出`

2. 点击后弹出轻量菜单

- `导入变量表`
- `导出 JSON`
- `导出 CSV`

#### 交互形式建议

优先使用：

- 下拉菜单

不建议继续平铺三个按钮。

#### 结果

- 头部空间更干净
- 视觉层级更明确
- 不再喧宾夺主

## 实施顺序

建议按下面顺序做，避免互相打架：

1. 先改 `Sidebar`

- 结果变量单条折叠
- 变量表按钮合并

2. 再改 `ProjectRunner`

- 步骤结果折叠
- 运行记录移入详细视图

3. 最后改状态语义

- 收掉紧凑模式里的 `依赖待更新`
- 详细模式再保留说明

4. 同步清理实现

- `ProjectRunner` 改用共享 `AutoResizeTextarea`

## 验收标准

### Sidebar

- 长结果变量不会再把其他变量整体顶走
- 单条结果变量支持展开/收起
- 变量表入口合并后仍能完成导入、导出 JSON、导出 CSV

### ProjectRunner

- 步骤结果支持折叠
- 长结果不会再让卡片始终超高
- 运行记录在紧凑模式下不显示
- 运行记录在详细模式下完整保留

### 状态语义

- 紧凑模式头部不再出现旧变量同步语义造成的误导标签
- 详细模式仍能看懂依赖关系

### 高度行为

- 步骤结果框展开后高度自适应稳定
- 不再出现明显的 `n + x` 行空白

## 建议结论

这轮不需要发明新功能，重点是把已经有的能力重新分层。

我建议下一步直接开做，顺序就是：

1. `Sidebar` 结果变量折叠 + 变量表按钮合并
2. `ProjectRunner` 步骤结果折叠 + 运行记录移入详细视图
3. 收掉紧凑模式里的 `依赖待更新`

这是当前最值的一轮体验优化。
