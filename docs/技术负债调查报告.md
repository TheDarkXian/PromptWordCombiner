# 技术负债调查报告

## 调查范围

本次调查基于仓库当前工作区，覆盖以下内容：

- 前端主代码：`App.tsx`、`components/`、`domain/`、`services/`
- 桌面端壳层：`src-tauri/`
- 工程配置：`package.json`、`README.md`、`.gitignore`、`tsconfig.json`、`vite.config.ts`
- 文档索引：`docs/README.md`

本次未做完整功能回归，只做了静态结构检查与一次 `cmd /c npm run typecheck` 验证。类型检查当前通过，但这不能覆盖运行时、打包链路和桌面端集成风险。

## 总体结论

项目当前的技术负债不是单点问题，而是四类问题叠加：

1. 仓库治理和可复现性不足，已经影响桌面端能力的可维护性。
2. 核心 UI 入口承担了过多状态与业务职责，重构成本在持续抬升。
3. 领域逻辑与展示逻辑边界不清，重复实现已经出现。
4. 质量保障体系几乎空白，现阶段主要依赖人工回归。

如果继续在当前结构上直接叠加功能，后续最容易出现的问题不是“写不出来”，而是：

- 一个改动要同时触碰多个大文件
- 同一规则在不同组件中逐渐分叉
- 打包、发布、迁移环境时出现不可复现问题
- 缺陷只能靠人工发现，修复后也缺少回归保护

## 重点负债

### 一、桌面端壳层未被完整纳入版本控制

严重级别：高

证据：

- 顶层 `.gitignore` 忽略了 `src-tauri/*`，仅对白名单文件放行。
- `git ls-files src-tauri` 当前只有 `src-tauri/capabilities/default.json` 和 `src-tauri/tauri.conf.json`。
- `git check-ignore -v src-tauri\\src\\main.rs` 显示该文件被顶层 `.gitignore` 第 47 行规则忽略。
- `src-tauri/Cargo.toml`、`src-tauri/src/main.rs`、`src-tauri/src/lib.rs` 真实存在于工作区，但不在 Git 跟踪范围内。

影响：

- 桌面端壳层代码、Rust 依赖和插件接入无法随仓库完整复现。
- 新环境拉取仓库后，Tauri 侧能力并不完整，发布链路依赖“本地已有文件”。
- 一旦本地文件丢失、切机、协作或 CI 介入，桌面端构建会立即失稳。

建议：

- 取消对 `src-tauri/Cargo.toml`、`src-tauri/src/**`、`src-tauri/build.rs` 的忽略。
- 仅保留对 `src-tauri/target/`、`src-tauri/gen/schemas/` 这类生成产物的忽略。
- 先把当前本地 Tauri 源文件补入版本控制，再补一条最小可运行的桌面端构建说明。

### 二、工程可复现性和仓库治理存在明显缺口

严重级别：高

证据：

- `package.json` 只有 `dev`、`build`、`preview`、`typecheck`、`lint`，其中 `lint` 实际等同于 `tsc --noEmit`。
- 仓库没有任何项目级 `*.test.*` 或 `*.spec.*` 文件。
- `README.md` 只有极简运行说明，并且步骤写成了 `npm run dev` 后接 `4.tauri run`，缺少 Tauri CLI、构建方式、发布方式和环境约束。
- 顶层 `.gitignore` 忽略了 `package-lock.json`，但该文件又已被 Git 跟踪，规则与现实状态不一致。

影响：

- 工程没有真正的 lint、单元测试、集成测试、打包冒烟测试。
- 开发者只能靠手工点击确认功能是否正常。
- 锁文件策略不明确，后续依赖升级和环境迁移容易产生“我这里能跑，你那里不能跑”的分歧。

建议：

- 明确锁文件策略：保留并跟踪 `package-lock.json`，同时移除对应忽略规则。
- 将 `lint` 改成真实静态检查，至少引入 ESLint。
- 增加最小测试面：先覆盖 `domain/`、`services/` 的纯函数逻辑。
- 重写 `README.md`，明确 Node 版本、Tauri CLI 依赖、本地开发命令、桌面端运行命令、打包命令。

### 三、核心入口和关键组件体量过大，职责已经失衡

严重级别：高

证据：

- `App.tsx` 约 1313 行。
- `components/TemplateEditor.tsx` 约 1492 行。
- `components/ProjectRunner.tsx` 约 882 行。
- `components/SettingsModal.tsx` 约 650 行。
- `components/Sidebar.tsx` 约 502 行。
- `components/FileLibrary.tsx` 约 525 行。

从代码职责看，`App.tsx` 同时承担了：

- 初始化加载
- 持久化节流保存
- 项目、模板、设置三类核心状态管理
- 批量执行流程控制
- 弹窗控制
- 执行步骤调度
- 大量跨模块联动更新

影响：

- 任何新功能都更容易把状态耦合到入口文件。
- 变更影响面难以预估，局部修改需要理解整段控制流。
- 大型组件的 review、测试、重构成本都在增加。

建议：

- 先拆 `App.tsx`，优先抽离 `useAppPersistence`、`useBatchRun`、`useModalState`、`useProjectActions`。
- 对 `TemplateEditor`、`ProjectRunner`、`SettingsModal` 采取“容器 + 分区子组件”拆分。
- 约束单文件职责，避免继续把业务规则堆回 UI 组件。

### 四、领域逻辑分层不彻底，重复实现已经出现

严重级别：中高

证据：

- `services/interpolationService.ts` 已经提供了插值能力。
- `components/ProjectRunner.tsx` 第 212 行开始又单独实现了一套 `interpolate` 逻辑。
- `ProjectRunner` 内还包含 `getStepStatus`、`getDependencyState` 等业务判断，它们本质上更接近领域规则，而不是展示逻辑。
- `App.tsx` 直接编排 `executeProjectStep`、批量执行、变量同步、持久化联动，说明应用服务层偏薄。

影响：

- 同一规则如果后续修改，很容易出现一处更新、一处遗漏。
- 组件越大，越倾向继续复制逻辑而不是复用已有服务。
- 领域规则难以脱离 UI 做单元测试。

建议：

- 把步骤依赖分析、插值、步骤状态判定、批量执行编排提取到独立应用服务。
- `components/ProjectRunner.tsx` 只保留展示状态和事件分发。
- 对可纯函数化的规则统一放入 `domain/` 或 `services/`，避免“UI 内嵌业务规则”继续蔓延。

### 五、国际化与文案管理集中度不够，存在维护分叉风险

严重级别：中

证据：

- `services/i18n.ts` 约 825 行，已经是单文件大词典。
- 同时多个组件仍保留硬编码文案，例如 `SettingsModal.tsx` 中仍有 `App Settings`、`Interface`、`Testing...`、`Test` 等直接字符串。
- 项目整体存在中英文混用，说明国际化还处于“部分接管”状态。

影响：

- 文案调整要同时搜索词典和组件代码。
- 新增语言或统一术语时，容易漏改。
- i18n 文件持续膨胀后，冲突频率会升高。

建议：

- 先完成“禁止新增硬编码文案”的收口。
- 按模块拆分词典，例如 `project`、`sidebar`、`templateEditor`、`settings`。
- 补一份术语表，避免同一概念中英文说法不一致。

### 六、I/O 与模型调用服务缺少更强的错误边界和类型边界

严重级别：中

证据：

- `services/ioService.ts` 大量使用 `any`，并在多个分支中直接吞掉异常后只做 `console.error`。
- `saveToDisk` 的 Tauri 分支内部捕获异常后不再向上抛出，调用方无法准确知道失败原因。
- `services/providerExecution.ts` 直接用 `fetch` 请求不同提供商，但没有超时、取消、重试、限流等统一策略。
- `providerExecution.ts` 中对 OpenAI 兼容协议和 Anthropic 协议做了两套实现，但抽象层仍比较薄，未来增加更多提供商时会继续膨胀。

影响：

- 运行时错误更多地表现为“某一步没成功”，而不是可诊断的系统状态。
- 失败恢复策略难统一，批量执行场景尤其脆弱。
- 服务层越薄，调用方越容易直接补临时逻辑。

建议：

- 为 I/O 服务改成显式返回 `Result` 风格或统一错误对象。
- 为模型执行增加超时和可取消机制。
- 把提供商协议差异隔离为 provider adapter，避免入口函数持续变大。

## 负债优先级建议

### 第一优先级：1 周内处理

- 修正 `src-tauri` 版本控制策略，补齐 Rust 侧源码与配置
- 明确并统一锁文件策略
- 重写 `README.md` 的开发与构建说明
- 增加最小 lint 体系

### 第二优先级：1 到 2 个迭代处理

- 拆分 `App.tsx`
- 拆分 `TemplateEditor.tsx` 与 `ProjectRunner.tsx`
- 抽离批量执行、步骤状态分析、插值、变量同步等应用服务

### 第三优先级：持续治理

- 建立项目级测试基线
- 拆分 i18n 词典
- 统一错误处理模型和日志模型

## 建议的落地顺序

1. 先修仓库治理问题，再做结构重构。否则重构成果仍然不可复现。
2. 再补质量闸门，至少做到“改纯逻辑有测试，改 UI 有类型和 lint 约束”。
3. 最后拆大组件和分层，因为这一步会改变文件边界，适合在最基本的工程护栏建立后推进。
