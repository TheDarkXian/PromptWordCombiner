# PromptWordSplicer 变量系统重构方案

## 1. 背景

当前项目已经能完成：

- 模板输入变量替换
- 项目局部变量补充
- 步骤输出引用
- 项目级覆盖编辑

但在真实使用中，存在一个关键断点：

很多“变量”并不是用户一开始就知道的静态值，而是要先通过某个步骤生成，再作为后续步骤的输入继续复用。  
当前系统虽然支持 `[[步骤输出]]` 直接引用，但步骤输出还没有被正式抽象为“可管理变量”，因此用户仍然需要：

1. 复制某一步提示词
2. 到外部 AI 工具执行
3. 取回结果
4. 手工粘贴到步骤输出或变量中

这导致系统的工作流是“可拼接，但不可真正流转”。

## 2. 设计目标

这次重构的目标不是单纯增加更多变量，而是把变量系统从“手工填写容器”升级成“项目运行时上下文系统”。

具体目标：

1. 让变量不再只有静态输入一种来源。
2. 让步骤输出可以被正式声明为变量来源。
3. 让后续 AI 执行层可以直接把模型结果写回上下文。
4. 让用户能清楚知道某个值来自哪里，是手填、步骤生成、还是派生结果。
5. 保持现有模板和项目数据可平滑迁移，不推翻现有使用方式。

## 3. 当前问题

### 3.1 变量与步骤输出是两套体系

现在项目里主要有：

- `inputValues`
- `customInputs`
- `stepOutputs`

它们都能参与拼接，但语义不同、来源不同、管理方式也不同。  
问题在于：

- `inputValues` 更像静态表单
- `customInputs` 更像临时补丁
- `stepOutputs` 更像运行结果

但在真实工作流里，这三者常常会互相转化。

### 3.2 缺少“来源”抽象

当前一个变量值只有“当前值”，没有“来源信息”。  
系统并不知道一个值是：

- 用户手填
- 模板默认值
- 某个步骤结果
- 某个步骤结果截断/整理后的派生值

没有来源信息，后续就难以支持：

- 自动回填
- 失效提示
- 重新运行后联动更新
- 调试与追踪

### 3.3 步骤输出虽然可引用，但不便于复用

`[[1]]` 和 `[[步骤名]]` 的方式适合快速写链路，但不适合长期维护。  
原因是：

- 依赖步骤顺序
- 文本引用不够结构化
- 无法表达“只取这个输出里的某个字段”
- 不能很好地沉淀成稳定变量

### 3.4 当前系统偏“拼 prompt”，不够“跑流程”

它现在更像提示词资产工具，而不是执行上下文系统。  
这没有错，但如果后续要接入文本模型，就必须让变量层升级，否则 AI 执行只会停留在“自动把结果写进备注框”。

## 4. 重构方向

建议把“变量”从字段层提升为统一上下文对象。

也就是：

- 不再把变量只理解为模板输入框
- 而是把它理解为“项目在运行过程中可被引用的命名值”

这个统一上下文里，值可以来自不同来源。

## 5. 变量分类

建议把变量分成四类。

### 5.1 静态输入变量

用途：

- 由用户显式填写
- 在项目启动时就存在
- 常用于主题、风格、约束、客户要求等

来源：

- 模板输入定义
- 模板默认值
- 用户手工修改

示例：

- `topic`
- `style`
- `language`

### 5.2 项目局部变量

用途：

- 在单个项目中临时增加
- 不回写模板
- 用来承接某次任务的补充信息

来源：

- 用户临时创建
- 用户手工填写

示例：

- `客户额外要求`
- `本轮限制词`

这类变量本质上保留现有 `customInputs` 的功能，但应被纳入统一变量系统。

### 5.3 步骤输出变量

用途：

- 把某一步的结果正式变成可引用变量
- 作为后续步骤的稳定输入

来源：

- 手工填写步骤输出
- AI 执行结果自动回填

示例：

- `scene_description`
- `draft_outline`
- `prompt_en`

这是这次重构最关键的部分。

### 5.4 派生变量

用途：

- 从已有变量或步骤输出中加工得到
- 用于避免反复手工裁剪和重写

来源：

- 某个字段提取规则
- 某个格式化规则
- 未来可由 AI 或本地函数生成

示例：

- `short_title`
- `keywords_csv`
- `negative_prompt`

这类变量不是第一阶段必须完成，但数据模型应预留位置。

## 6. 建议的数据结构

建议后续逐步从“散字段”迁移到统一上下文结构。

### 6.1 建议新增的变量对象

```ts
type VariableSourceType =
  | 'template_input'
  | 'project_local'
  | 'step_output'
  | 'derived'
  | 'manual';

interface ProjectVariable {
  id: string;
  key: string;
  label: string;
  value: string;
  sourceType: VariableSourceType;
  sourceRef?: string;
  createdAt: number;
  updatedAt: number;
}
```

字段说明：

- `key`: 稳定引用名，推荐英文或稳定 slug
- `label`: 界面展示名，可中文
- `value`: 当前值
- `sourceType`: 变量来源类别
- `sourceRef`: 来源引用，例如某个步骤 id

### 6.2 建议项目层新增字段

```ts
interface Project {
  ...
  variables: ProjectVariable[];
}
```

保留旧字段一段时间用于兼容迁移：

- `inputValues`
- `customInputs`
- `stepOutputs`

最终目标是让它们在运行时都映射进 `variables`。

### 6.3 建议步骤层新增输出声明

模板步骤建议补一个输出定义：

```ts
interface StepOutputBinding {
  mode: 'none' | 'variable';
  variableKey?: string;
  variableLabel?: string;
}

interface TemplateStep {
  ...
  outputBinding?: StepOutputBinding;
}
```

意思是：

- 有的步骤只是中间过程，不需要沉淀变量
- 有的步骤执行完，应直接把结果写成某个变量

例如：

- 步骤 1 输出绑定 `scene_description`
- 步骤 2 输出绑定 `image_prompt_en`
- 步骤 3 输出绑定 `negative_prompt`

## 7. 引用语法建议

现有语法不要立即废弃，但要逐步补强。

### 7.1 保留旧语法

- `<0>`
- `<变量名>`
- `<l1>`
- `[[1]]`
- `[[步骤名]]`

这样不会打断现有项目。

### 7.2 新增稳定变量语法

建议新增统一变量引用语法：

```text
{{variable_key}}
```

示例：

- `{{topic}}`
- `{{scene_description}}`
- `{{negative_prompt}}`

理由：

- 不依赖顺序
- 更稳定
- 更适合 AI 执行层
- 更适合后续可视化检查

### 7.3 语法优先级建议

后续插值顺序建议为：

1. `{{variable_key}}`
2. `<变量名>` / `<序号>` / `<l序号>`
3. `[[步骤编号]]` / `[[步骤名]]`

这样新旧机制可以并存，逐步迁移。

## 8. 用户交互建议

### 8.1 左侧栏从“变量表单”升级为“项目上下文”

建议把当前变量区改造成三段：

- 输入变量
- 局部变量
- 结果变量

结果变量应明确展示：

- 来自哪个步骤
- 当前值是否最新
- 是否允许手工覆写

### 8.2 步骤编辑区增加“输出绑定”

每个步骤应允许配置：

- 不绑定变量
- 绑定到已有变量
- 创建一个新的结果变量

这一步会直接决定它是不是“流程节点”。

### 8.3 提供“回填为变量”操作

即使在完全手工模式下，也应该允许用户把某步输出一键登记成变量。  
这样即使还没接 AI 执行，也能先改善你的当前工作流。

建议按钮：

- `写入结果变量`
- `新建变量并写入`

### 8.4 标记失效状态

如果上游步骤重新运行或被修改，依赖它的变量应有失效提示。  
第一阶段不一定要自动级联更新，但至少应让用户看到：

- 当前值来自旧结果
- 当前值可能已过期

## 9. 与 AI 执行层的关系

这次重构的真正价值，是给 AI 执行层铺路。

未来接入 `OpenAI / Claude` 后，理想流程应是：

1. 用户填写静态输入变量
2. 点击运行步骤 1
3. 模型返回文本
4. 系统自动写入步骤输出
5. 如果该步骤配置了输出绑定，则自动同步到某个变量
6. 后续步骤通过 `{{variable_key}}` 继续引用

这样项目才会从“提示词编辑器”升级成“可执行工作台”。

## 10. 分阶段实施建议

### 第一阶段：统一变量模型，但不接 AI

目标：

- 新增 `variables` 结构
- 把旧输入、局部变量、步骤输出映射进统一变量视图
- 新增 `{{variable_key}}` 引用
- 提供“步骤输出写入变量”能力

这一步做完，你手工工作流就已经会顺很多。

### 第二阶段：步骤输出绑定

目标：

- 模板步骤可声明输出绑定
- 某一步的结果自动写入目标变量
- 变量来源信息可追踪

这一步做完，项目结构就开始真正流程化。

### 第三阶段：AI 执行接入

目标：

- 单步执行文本模型
- 结果自动回填
- 支持 `OpenAI / Claude`

这一步才是模型集成，不建议跳过前两步直接上。

### 第四阶段：派生变量

目标：

- 从上游变量自动生成格式化结果
- 支持文本裁剪、拼接、清洗、结构提取

这是更高级的工作流能力，可以后置。

## 11. 风险与取舍

### 11.1 不要一次性推翻旧语法

如果强制全部改成新变量系统，会打断现有资产。  
建议兼容旧语法，逐步迁移。

### 11.2 不要先做节点画布

节点画布解决的是“可视化表达”，不是“上下文流转”。  
当前瓶颈在变量流，不在画布。

### 11.3 不要先做复杂派生逻辑

第一阶段只要能让“步骤结果成为正式变量”就已经足够有价值。

## 12. 推荐结论

下一步最值得做的不是先接模型，而是：

1. 先把变量系统升级成统一上下文模型
2. 让步骤输出可以绑定为变量
3. 再接入 `OpenAI / Claude` 文本执行

对你当前的真实使用方式来说，这会比先接 API 更有效。  
因为它先解决了“结果如何流转”的问题，之后模型接入才真正能释放效率。
