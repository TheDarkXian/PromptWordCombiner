# 蓝图节点升级测试方案

## 1. 目标与范围

本方案用于验证“节点蓝图化升级”在当前项目中的可用性、正确性与回归风险，覆盖以下范围：

- 节点图构建与边推导（变量引用驱动）。
- 生产节点筛选与执行顺序（拓扑排序）。
- 阻塞、循环依赖、范围过滤等异常路径。
- 与现有模板编辑器、项目运行器的状态一致性。
- 升级前后数据兼容与存量模板可回放。

不在本轮范围：

- 复杂视觉美术验收（仅做功能可用性验证）。
- 新模型能力扩展（生图/生视频）。

## 2. 测试对象

- 数据结构与图语义：`types.ts` 中 `StepGraphNode/StepGraphEdge`。
- 图服务：`services/stepGraphService.ts`。
- 运行与预检查相关 UI：
  - `components/project-runner/ProducerRunPreflightModal.tsx`
  - `components/project-runner/ProducerRunProgressModal.tsx`
  - `components/ProjectRunner.tsx`
- 模板编辑链路：
  - `components/TemplateEditor.tsx`
  - `components/template-editor/TemplateStepCard.tsx`

## 3. 测试环境

- 系统：Windows（开发主环境）
- Node.js：22.x（与仓库要求一致）
- 包管理：npm
- 核心命令：
  - `npm run typecheck`
  - `npm run lint`
  - `npm run test`
  - `npm run build`
  - 回归总检：`npm run verify`

## 4. 测试分层

## 4.1 单元测试（核心逻辑）

目标：锁定图构建与排序算法行为，避免 UI 变更掩盖逻辑问题。

建议新增/补强：

- `buildStepGraph`
  - 正常链路：A->B->C 三节点有向边正确。
  - 多输入聚合：C 同时依赖 A/B 输出。
  - 无输出步骤：应标为 `consumer` 或 `passthrough`。
  - 重名变量生产者：多生产者映射行为可预期。
- `getProducerCandidates`
  - 仅 `text_generation + autoRunEnabled=true + outputBinding` 入选。
  - `manual/external` 不应误入选。
- 稳定拓扑排序
  - 同层节点按模板顺序稳定输出。
  - 环检测返回循环节点并触发预期阻塞原因。

完成标准：核心函数分支覆盖率 >= 85%（语句和分支）。

## 4.2 集成测试（编辑-预检查-执行链路）

目标：验证从模板编辑到运行结果的全链路一致性。

关键场景：

- 新增步骤并绑定输出变量后，预检查列表即时反映新增生产节点。
- 修改变量引用后，上下游关系实时更新，旧依赖不残留。
- `empty_only / changed_only / all` 三种 scope 的节点入队一致。
- 停止执行后，后续节点状态文案与日志一致。
- 结构化输出覆盖确认框与执行结果一致。

## 4.3 端到端冒烟（桌面工作流）

目标：覆盖真实用户关键路径。

场景脚本：

1. 创建模板（3-5 步，含生产与消费关系）。
2. 执行一次全量。
3. 修改中游步骤提示词，执行 `changed_only`。
4. 人工停止执行，确认队列与提示一致。
5. 导出结果并核对节点结果映射。

通过标准：关键路径零阻断、无崩溃、无数据丢失。

## 5. 用例矩阵（最小集合）

| 编号 | 类别 | 用例描述 | 期望结果 |
| --- | --- | --- | --- |
| BG-001 | 图构建 | 单链路变量依赖 | 边与上下游正确 |
| BG-002 | 图构建 | 多上游汇聚 | C 有两个上游 |
| BG-003 | 筛选 | 非 text_generation 步骤 | 不进入生产候选 |
| BG-004 | 排序 | 同层无依赖多节点 | 顺序稳定且可预测 |
| BG-005 | 异常 | 循环依赖 A<->B | 预检查阻塞并给出原因 |
| BG-006 | 范围 | changed_only | 仅变化节点及必要依赖执行 |
| BG-007 | 交互 | 运行中停止 | 后续节点标记未执行 |
| BG-008 | 兼容 | 旧模板加载 | 图语义可重建，无报错 |

## 6. 兼容性与迁移验证

- 准备 3 份历史模板样本：
  - 简单线性模板
  - 多变量交叉模板
  - 含手动步骤模板
- 对每份样本执行：
  - 加载成功
  - 图构建成功
  - 预检查成功
  - 至少一次运行成功
- 记录升级前后关键字段快照（步骤 ID、变量 key、执行状态）。

## 7. 非功能测试

- 性能：50/100/200 步模板下，预检查耗时与 UI 可交互性。
- 稳定性：连续 30 次预检查与执行切换，不出现内存异常增长。
- 可观测性：日志包含 stepId、scope、阻塞原因、停止事件。

## 8. 缺陷分级与准入准出

- P0：崩溃、数据损坏、错误执行链路。
- P1：错误阻塞/漏执行、结果错位。
- P2：UI 状态不同步、提示文案错误。
- P3：低影响视觉/文案细节。

准入条件：

- P0=0、P1=0。
- P2 可控且有明确修复排期。
- 回归总检 `npm run verify` 通过。

## 9. 执行节奏建议

1. 第 1 天：补齐/修正单元测试，锁定图语义。
2. 第 2 天：集成测试与关键交互回归。
3. 第 3 天：E2E 冒烟、兼容样本回放、缺陷收敛。
4. 第 4 天：灰度验收与发布评审。

## 10. 交付物

- 测试用例清单（含执行结果）。
- 缺陷列表（含分级与复现步骤）。
- 升级回归报告（含准入结论：通过/不通过）。
