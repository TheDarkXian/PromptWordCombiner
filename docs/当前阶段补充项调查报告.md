# PromptWordSplicer 当前阶段补充项调查报告

## 1. 调查范围

本报告基于当前仓库已经落地的几条主线能力进行盘点：

- 模板编辑与变量系统
- 单步生成与生产节点自动化
- 结构化输出阶段 A / B
- 项目页与侧边栏的高频交互
- 现有文档中已经确认过的产品路线

重点不是重新发散新方向，而是判断：

1. 当前阶段已经做到了什么  
2. 还缺哪些“高价值补充项”  
3. 哪些适合马上做，哪些应该暂缓

## 2. 当前阶段的真实状态

从代码和现有文档看，这个产品现在已经不是简单的提示词拼接器，而是一个比较完整的“本地 AI 文本生产工作台”：

- 模板、变量、步骤、项目实例已经成体系
- 文本模型的单步生成已经接入
- 生产节点自动化已经具备预检查、拓扑排序、队列状态和停止能力
- 结构化输出已经进入阶段 B，支持整段结果二次解析并回填字段/变量

这说明产品主链已经从“手工管理提示词”进入“半自动生成中间文本资产”的阶段。

## 3. 当前最值得补的内容

这一部分只列“现在做了就明显增值”的补充项。

### 3.1 结构化输出的人工控制层

结构化输出阶段 B 已经实现“整段结果 -> 自动解析 -> 字段 -> 变量”，但仍缺少几项高频控制：

- `重新解析字段`
  - 当前结构化解析主要挂在生成成功后自动触发
  - 缺一个显式入口，让用户在不重跑整段结果的前提下，只重跑结构化解析
- `仅解析当前字段空项`
  - 现在是整步覆盖/跳过
  - 对长字段集来说颗粒度还偏粗
- `解析结果校对感`
  - 当前字段会被自动写入，但“哪些字段是刚自动更新的”不够直观
  - 后续可以补局部高亮或一次性变更摘要

这是当前最值得补的一组，因为结构化输出已经进入可用阶段，接下来最缺的是“可控性”和“可复查性”。

### 3.2 批量结果导出增强

当前产品已经支持：

- 批量实例化
- 批量执行
- 生产节点自动化

但“跑完之后怎么把结果拿走”这一层还不够强。

最值得补的是：

- 按步骤导出批量结果
- 导出整段结果
- 导出结构化字段结果
- 导出变量值
- 支持 `CSV / JSON / Markdown`

特别是在结构化字段已经存在的前提下，这一项的价值更高，因为它能直接把中间文本资产转成“可交付数据”。

### 3.3 结构化字段进入批量视角

当前结构化字段已经能在单项目里看和改，但还没有真正进入批量工作面。

值得补的是：

- 在批量执行结果面板里显示字段解析状态
- 在批量结果导出里把字段作为列导出
- 在项目列表/批量视图中显示某些关键字段摘要

这会让结构化输出不只是“单步骤局部增强”，而是真正进入生产链。

### 3.4 自动化状态和结果解释继续收口

生产节点自动化已经做到了：

- 队列中
- 运行中
- 成功
- 失败
- 已跳过
- 已阻塞
- 已停止

但后续还有两层值得补：

- 更清晰的“为什么跳过”
  - 不在范围
  - 已有结果未覆盖
  - 用户停止后未继续
- 更清晰的“为什么阻塞”
  - 缺变量
  - 模型不可执行
  - 循环依赖

这部分不是新能力，而是把已有自动化做得更适合高频使用。

### 3.5 项目级“文本资产检查”视图

当前很多状态分散在步骤卡片里：

- 哪些步骤有结果
- 哪些变量已更新
- 哪些结构化字段未整理
- 哪些生产节点可自动执行

值得补一个更轻量的项目级检查面板，像一个“中间文本资产总览”：

- 生产节点数量
- 已生成数量
- 已结构化数量
- 待整理字段数量
- 阻塞数量

这会比继续在步骤头部堆标签更有效。

## 4. 中期值得补的内容

这些也值得做，但优先级略低于上面的主链补强。

### 4.1 解析提示词可配置

现在结构化解析提示词是统一生成的，第一版这是对的。  
但后续可能会遇到：

- 某类字段需要更强约束
- 某类步骤的结构化提取方式和默认模板不完全适配

所以中期可以考虑：

- 提供步骤级解析提示词附加说明
- 或提供全局解析模板

但这不应优先于“重新解析”和“批量导出”。

### 4.2 变量来源跳转

现在变量系统已经很强，但一旦结构化字段多了，用户更容易问：

- 这个字段变量是从哪个步骤来的？
- 是整段结果来的还是结构化字段来的？

值得补：

- 从变量跳回来源步骤
- 从字段绑定跳到对应变量

### 4.3 结果对比

当自动化执行或重新解析多次发生时，后续很值得补：

- 上一次整段结果 vs 这一次整段结果
- 上一次字段结果 vs 这一次字段结果

这对调 prompt、调字段定义都会有帮助。

## 5. 当前不建议优先做的内容

以下方向并不是没价值，而是当前阶段投入产出比不高。

### 5.1 蓝图式节点画布

底层节点图语义已经有了，但现在最紧缺的不是“画出来”，而是：

- 结构化结果更好承接
- 批量结果更好利用
- 自动化状态更好解释

所以画布仍然应保持在后续阶段。

### 5.2 生图 / 生视频模型正式接入

从产品路线看，这肯定是未来方向。  
但当前更紧缺的是前半段文本资产链的稳定性：

- 生产节点自动化
- 结构化字段承接
- 批量结果导出

如果这三层还没稳，过早接图像/视频模型会把复杂度放大。

### 5.3 全自动 Agent 编排

当前最适合的自动化深度仍然是：

> 受控的半自动文本资产生成

而不是全自动代理型工作流。

## 6. 调查结论

如果只按当前阶段选最值得继续做的三件事，我建议顺序是：

1. `批量结果导出增强`
2. `结构化输出的人工控制层（重新解析 / 更细粒度覆盖）`
3. `项目级文本资产检查视图`

原因是：

- 第一项直接提升“跑完之后怎么用”
- 第二项直接提升“结构化输出怎么控”
- 第三项直接提升“项目里哪些资产已经成型”

这三件都比继续扩更多模型或切画布更贴当前主线。

## 7. 建议的下一步

建议下一份正式计划优先写成：

- `批量结果导出增强实施方案`

因为这一步和当前已经做好的：

- 生产节点自动化
- 结构化输出阶段 A/B
- 变量系统

三者都能直接衔接，而且用户价值最直观。
