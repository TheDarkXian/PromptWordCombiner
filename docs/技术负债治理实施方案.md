## 1. 方案目标

本方案不是一次“全面重写”，而是一次按风险优先级推进的工程治理。目标有四个：

1. 修复当前最危险的不可复现问题，确保仓库可拉取、可构建、可协作。
2. 建立最小质量护栏，避免后续重构继续靠人工回归兜底。
3. 拆解核心大文件，把高频变更点从 UI 巨石中解耦出来。
4. 让后续功能开发基于稳定结构继续演进，而不是在现有耦合上叠加。

本方案默认采用“小步提交、阶段验收、每阶段可独立结束”的方式推进。

## 2. 治理原则

### 2.1 先修复现性，再做结构优化

如果 `src-tauri`、依赖锁定、运行说明都不稳定，后续所有结构优化都无法可靠交付给别人，也无法稳定进入 CI。

### 2.2 先补护栏，再动大结构

对 `App.tsx`、`TemplateEditor.tsx`、`ProjectRunner.tsx` 的拆分会引起大范围移动。没有 `lint`、测试和最基本构建校验时，拆分成本会失控。

### 2.3 优先抽纯逻辑，不先抽抽象

先把插值、步骤状态、批量执行、变量同步、导入校验这类“可纯函数化”的逻辑下沉，再判断是否需要状态层或更复杂架构。

### 2.4 每个阶段都必须有清晰完成定义

每一阶段都要有：

- 明确改动范围
- 明确交付物
- 明确验收标准
- 明确回滚边界

## 3. 范围与非目标

### 3.1 本次纳入范围

- 仓库治理
- Tauri 壳层纳管
- 依赖与脚本治理
- README 与开发流程文档
- 基础质量体系
- 关键组件拆分
- 领域/服务边界梳理
- 国际化与错误处理治理

### 3.2 本次不纳入范围

- 全量 UI 视觉重做
- 状态管理库替换为大型方案
- 多端同步或云端能力
- Provider 能力扩展到更多新平台
- 全量历史文档重写

## 4. 总体里程碑

建议按五个里程碑推进：

1. M1 仓库可复现性达标
2. M2 质量护栏上线
3. M3 核心结构拆分完成
4. M4 服务边界与稳定性治理完成
5. M5 文案/国际化/文档治理收口

建议推进顺序必须严格按 M1 -> M2 -> M3 -> M4 -> M5，不建议并行乱改。

## 5. Phase 1：仓库与构建治理

### 5.1 目标

解决当前最危险的问题：仓库拉下来后不能完整复现桌面端能力，依赖锁定策略不清晰，开发入口说明不足。

### 5.2 具体问题

- `src-tauri` 的 Rust 源码和 `Cargo.toml` 未被 Git 完整跟踪。
- `.gitignore` 对 `package-lock.json` 的忽略与当前事实状态冲突。
- `README.md` 只有极简说明，不足以支撑协作开发。
- 现有脚本缺少面向桌面端的清晰入口。

### 5.3 实施任务

#### 任务 A：修正 `.gitignore` 与 `src-tauri` 纳管策略

目标：

- 让 Tauri 壳层源码成为正式仓库资产。

改动范围：

- `.gitignore`
- `src-tauri/Cargo.toml`
- `src-tauri/build.rs`
- `src-tauri/src/lib.rs`
- `src-tauri/src/main.rs`

实施方式：

1. 移除顶层 `.gitignore` 对 `src-tauri/*` 的总拦截。
2. 明确保留忽略项仅限：
   - `src-tauri/target/`
   - `src-tauri/gen/schemas/`
   - 其他明确生成产物
3. 将当前存在但未跟踪的 Tauri 核心文件纳入版本控制。
4. 复核 `src-tauri/.gitignore`，确保生成目录继续被忽略。

验收标准：

- `git ls-files src-tauri` 能看到 `Cargo.toml` 和 `src/**/*.rs`
- 新环境拉取仓库后具备完整桌面端源码

回滚边界：

- 若发现本地 `src-tauri` 文件包含不可公开内容，暂停提交并先做敏感信息筛查

#### 任务 B：统一锁文件策略

目标：

- 明确前端依赖以 `package-lock.json` 为准，避免依赖分歧。

改动范围：

- `.gitignore`
- `README.md`

实施方式：

1. 删除 `.gitignore` 中对 `package-lock.json` 的忽略。
2. 明确项目使用 `npm` 作为默认包管理器。
3. 在 `README.md` 中写清依赖安装与更新规范。

验收标准：

- 锁文件被正式视为仓库受控文件
- 新成员不会误删、误忽略锁文件

#### 任务 C：重写开发与构建说明

目标：

- 让仓库具备可直接操作的开发文档，而不是口头知识。

改动范围：

- `README.md`

建议至少补齐以下内容：

- 项目简介
- Node 版本要求
- Rust / Cargo / Tauri CLI 要求
- 安装依赖
- Web 开发启动
- Tauri 本地运行
- 生产构建
- 常见问题

验收标准：

- 新环境开发者可仅依赖 `README.md` 完成本地启动

### 5.4 阶段交付物

- 可复现的 Tauri 源码仓库
- 清晰一致的依赖管理策略
- 完整的开发/构建文档

## 6. Phase 2：质量护栏建设

### 6.1 目标

建立最小可用的工程护栏，保证后续拆分不是“盲改”。

### 6.2 具体问题

- `lint` 目前只是 `tsc --noEmit`
- 没有项目级测试
- 没有统一的构建前检查流程

### 6.3 实施任务

#### 任务 D：引入真实 lint

建议方案：

- 引入 ESLint
- 先覆盖 TypeScript、React Hooks、基础 import 规范

建议规则目标：

- 禁止未使用变量
- 禁止显式 `any` 新增扩散
- 约束 hooks 使用
- 约束重复导入和明显死代码

实施原则：

- 第一轮不要追求“零历史问题全部修完”
- 先以“新改动必须过 lint”为目标

验收标准：

- `npm run lint` 变成真实 lint 任务
- CI 或本地检查链路可稳定执行

#### 任务 E：补最小测试基线

优先测试对象：

- `domain/projectDomain.ts`
- `domain/templateDomain.ts`
- `services/interpolationService.ts`
- `services/executionAvailability.ts`
- `services/schemas.ts`

建议测试类型：

- 纯函数输入输出测试
- 边界值测试
- 迁移兼容测试

不建议第一轮就测：

- 大型组件交互细节
- 完整 Tauri UI 自动化

验收标准：

- 至少一套基础测试框架能运行
- 关键纯逻辑覆盖核心路径

#### 任务 F：统一本地校验脚本

建议脚本集合：

- `typecheck`
- `lint`
- `test`
- `build`
- 可选 `verify` 串联执行

验收标准：

- 本地和 CI 可以用同一组命令验证提交质量

### 6.4 阶段交付物

- 真正可用的 `lint`
- 第一批纯逻辑测试
- 统一校验命令

## 7. Phase 3：核心结构拆分

### 7.1 目标

把“大文件问题”从表象变成真正的职责重构，降低未来改动半径。

### 7.2 重点对象

- `App.tsx`
- `components/TemplateEditor.tsx`
- `components/ProjectRunner.tsx`
- `components/SettingsModal.tsx`
- `components/Sidebar.tsx`

### 7.3 实施策略

#### 任务 G：拆分 `App.tsx`

当前主要职责：

- 初始化加载
- 持久化
- 模态框控制
- 项目/模板/设置状态
- 步骤执行
- 批量运行

建议拆分目标：

- `hooks/useAppPersistence.ts`
- `hooks/useBatchRun.ts`
- `hooks/useModalState.ts`
- `hooks/useProjectActions.ts`
- `hooks/useTemplateActions.ts`

`App.tsx` 最终职责应收敛为：

- 组合 hooks
- 拼装页面级组件
- 传递必要事件

阶段验收标准：

- `App.tsx` 下降到约 400~600 行以内
- 业务逻辑不再主要堆在页面入口

#### 任务 H：拆分 `TemplateEditor.tsx`

建议拆分目录：

- `components/template-editor/TemplateEditorShell.tsx`
- `components/template-editor/TemplateMetaPanel.tsx`
- `components/template-editor/TemplateInputsPanel.tsx`
- `components/template-editor/TemplateModelRefsPanel.tsx`
- `components/template-editor/TemplateStepCard.tsx`
- `components/template-editor/ExecutionPresetPanel.tsx`

拆分原则：

- 容器组件保留状态与保存逻辑
- 复杂 UI 区块下沉
- 步骤卡片独立，避免一处改动影响整页

阶段验收标准：

- `TemplateEditor.tsx` 主文件降到 450 行左右
- 步骤相关 JSX 不再集中在单文件

#### 任务 I：拆分 `ProjectRunner.tsx`

建议拆分目录：

- `components/project-runner/ProjectRunnerShell.tsx`
- `components/project-runner/ProjectStepCard.tsx`
- `components/project-runner/ProjectDependencyBadge.tsx`
- `components/project-runner/ProjectRunLogPanel.tsx`
- `components/project-runner/ProjectPreviewPanel.tsx`

拆分重点：

- 日志面板独立
- 步骤卡片独立
- 右侧预览独立
- 运行状态与业务判断下沉到服务层

阶段验收标准：

- `ProjectRunner.tsx` 主文件降到 400~500 行
- 步骤状态逻辑不再内嵌全部 UI

#### 任务 J：拆分 `SettingsModal.tsx`

建议分区：

- 基础界面设置
- Provider 管理
- Model Catalog 管理
- Execution Preset 管理

阶段验收标准：

- 设置页每块职责分明
- 连接测试逻辑不再和大块 UI 全耦合

### 7.4 阶段交付物

- 主入口和关键组件明显瘦身
- 文件结构更稳定
- 后续功能可以按子模块演进

## 8. Phase 4：领域逻辑与服务边界治理

### 8.1 目标

消除重复实现和 UI 内嵌业务规则，让逻辑可复用、可测试。

### 8.2 实施任务

#### 任务 K：统一插值逻辑

问题：

- `services/interpolationService.ts` 和 `components/ProjectRunner.tsx` 现在有重复逻辑。

实施方式：

1. 扩展 `interpolationService.ts` 为唯一入口。
2. 补齐公共导出：
   - `interpolateText`
   - `createInterpolator`
   - `extractVariableKeys`
3. 删除组件内重复实现。

验收标准：

- 仓库只保留一套插值规则实现

#### 任务 L：下沉步骤状态与依赖分析

建议新增服务：

- `services/stepFlowService.ts`

承载逻辑：

- `getStepStatus`
- `getDependencyState`
- 与变量来源相关的判定逻辑

验收标准：

- 组件只负责展示状态，不负责定义状态

#### 任务 M：下沉批量执行编排

建议新增服务：

- `services/batchRunService.ts`

承载逻辑：

- 批量步骤执行流程
- 成功/失败聚合
- 导出数据准备

验收标准：

- `App.tsx` 不再直接承载大段批量执行控制流

#### 任务 N：统一 I/O 错误边界

建议：

- 让 `ioService.ts` 不再静默吞错
- 统一返回结构，例如：
  - `{ ok: true, data }`
  - `{ ok: false, error }`

后续 UI 层可以：

- 统一 toast
- 统一 modal
- 统一日志记录

验收标准：

- 调用层能明确知道失败原因，而不是只在控制台打印

#### 任务 O：抽 provider adapter

建议结构：

- `services/providers/openaiProvider.ts`
- `services/providers/anthropicProvider.ts`
- `services/providers/openaiCompatibleProvider.ts`
- `services/providerExecution.ts` 只做分发

验收标准：

- 新 provider 增加时不需要继续膨胀一个总文件

### 8.3 阶段交付物

- 单一来源的插值和步骤规则
- 更清晰的 I/O 和 provider 分层
- 更易测试的服务层

## 9. Phase 5：国际化、文案与文档治理

### 9.1 目标

把“部分接管”的国际化状态收口，降低后续文案维护摩擦。

### 9.2 实施任务

#### 任务 P：禁止新增硬编码文案

原则：

- 新增 UI 文案必须先进入 i18n
- 大型组件中的遗留硬编码逐步迁移

验收标准：

- 核心页面不再新增裸字符串

#### 任务 Q：拆分 `services/i18n.ts`

建议拆分目录：

- `services/i18n/project.ts`
- `services/i18n/sidebar.ts`
- `services/i18n/templateEditor.ts`
- `services/i18n/settings.ts`
- `services/i18n/fileLibrary.ts`
- `services/i18n/index.ts`

验收标准：

- 单文件词典不再持续膨胀
- 冲突面明显缩小

#### 任务 R：补术语与文档规范

建议新增：

- 术语对照表
- 文案风格约定
- 文档更新规则

验收标准：

- 中英文关键术语一致
- 新功能文档更易对齐

### 9.3 阶段交付物

- 模块化 i18n
- 更一致的产品文案
- 更稳定的项目文档维护方式

## 10. 建议排期

如果按单人或小团队节奏推进，建议采用以下节奏：

### Sprint 1

- Phase 1 全部完成
- Phase 2 的 lint 与脚本完成

### Sprint 2

- Phase 2 的测试基线完成
- Phase 3 启动，优先拆 `App.tsx`

### Sprint 3

- 完成 `TemplateEditor.tsx` 和 `ProjectRunner.tsx` 拆分
- 启动 Phase 4 的插值、步骤状态、批量执行服务下沉

### Sprint 4

- 完成 I/O、provider、错误边界治理
- 启动国际化和文案收口

### Sprint 5

- 收尾 Phase 5
- 统一回归、清理遗留兼容层、补文档

## 11. 验收清单

### M1 验收

- `src-tauri` 核心源码被 Git 跟踪
- `README.md` 可独立指导开发环境搭建
- 锁文件策略清晰一致

### M2 验收

- `npm run lint` 为真实 lint
- `npm run test` 可运行
- 关键纯逻辑具备基础测试

### M3 验收

- `App.tsx`、`TemplateEditor.tsx`、`ProjectRunner.tsx` 明显瘦身
- 关键大组件职责拆分完成

### M4 验收

- 插值、步骤状态、批量执行逻辑不再重复
- I/O 和 provider 具备清晰错误边界

### M5 验收

- 核心界面文案基本完成 i18n 接管
- 词典按模块拆分
- 项目文档和术语规范补齐

## 12. 风险与规避

### 风险 1：在没有护栏时直接拆大文件，导致行为回归

规避：

- 必须先完成 Phase 1 和 Phase 2 再进入 Phase 3

### 风险 2：一次性引入过多架构抽象，团队无法稳定跟进

规避：

- 优先纯函数和轻量 hooks，不先引入复杂状态框架

### 风险 3：兼容层长期残留，导致“新旧两套结构并存”

规避：

- 每个阶段结束时明确删除已替代旧实现

### 风险 4：治理期和功能需求冲突

规避：

- 治理期只允许低耦合功能插入
- 高风险业务需求延后到 M3 之后

## 13. 最终建议

如果只能先做三件事，优先顺序应为：

1. 修正 `src-tauri` 纳管和仓库治理
2. 建立 `lint + test + build` 的最小护栏
3. 拆 `App.tsx` 并下沉插值、批量执行、步骤状态逻辑

这三项做完后，后续所有优化才真正进入“可持续推进”状态，而不是继续在脆弱地基上施工。
