# PromptWordSplicer 代码架构与优化调查报告

调查日期：2026-05-02

## 1. 结论摘要

当前项目是一个以 `React 19 + TypeScript + Vite + Tauri 2` 为主的本地桌面工具，核心复杂度集中在前端状态管理和编辑器交互，Tauri/Rust 层非常薄，主要负责壳和插件接入。

整体判断：

- 产品功能已经超过 demo 阶段，具备可长期使用的本地工具形态。
- 代码当前还能维护，但已经出现明显的“大组件 + 大入口文件 + 逻辑重复”趋势。
- 近期最值得投入的不是继续堆功能，而是先做结构性拆分，否则后续功能会越来越难加、越来越难改。

## 2. 当前架构概览

### 2.1 技术栈

- 前端：`React 19`、`TypeScript`、`Vite`
- 桌面壳：`Tauri 2`
- 本地存储：`@tauri-apps/plugin-store` 或浏览器 `localStorage`
- 文件 I/O：`@tauri-apps/plugin-dialog`、`@tauri-apps/plugin-fs`

### 2.2 分层现状

可以概括成 4 层：

1. 应用入口与全局编排  
   由 [App.tsx](/E:/Project/Vscode/PromptWordSplicer/App.tsx:1) 承担，负责装载、归一化、持久化、页面切换、项目/模板写操作、执行调度。

2. 视图容器层  
   主要是 [components/TemplateEditor.tsx](/E:/Project/Vscode/PromptWordSplicer/components/TemplateEditor.tsx:1)、[components/ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:1)、[components/FileLibrary.tsx](/E:/Project/Vscode/PromptWordSplicer/components/FileLibrary.tsx:1)、[components/Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:1)。

3. 服务层  
   [services/ioService.ts](/E:/Project/Vscode/PromptWordSplicer/services/ioService.ts:1) 负责存储与文件交互；[services/modelService.ts](/E:/Project/Vscode/PromptWordSplicer/services/modelService.ts:1) 负责模型执行可用性判断和多供应商请求。

4. 桌面壳层  
   [src-tauri/src/lib.rs](/E:/Project/Vscode/PromptWordSplicer/src-tauri/src/lib.rs:1) 只做插件注册和启动，没有承载业务逻辑。

### 2.3 架构特点

- 优点：数据模型清晰，`Project` / `Template` / `Settings` 边界明确，业务上是“模板定义”和“项目实例”分离。
- 缺点：领域逻辑没有真正沉到 domain/service 层，很多逻辑仍然黏在 UI 组件里。

## 4. 主要问题与可优化点

### 4.1 `App.tsx` 过重，承担了应用编排之外的大量领域逻辑

[App.tsx](/E:/Project/Vscode/PromptWordSplicer/App.tsx:159) 内同时包含：

- 模板/项目归一化
- 变量同步
- 插值逻辑
- 执行调度
- 持久化触发
- 弹窗控制
- 页面装配

这会带来几个后果：

- 改一个业务规则，往往要进 `App.tsx`
- 很难做局部测试
- 子组件只能依赖大量 props 回调

建议优先拆出：

- `projectDomain.ts`：`syncProjectVariables`、`markStepOutputMeta`、`appendStepRunLog`
- `templateDomain.ts`：`normalizeTemplate`、`normalizeTemplateModelRefs`
- `interpolationService.ts`：统一管理 `{{var}}`、`<input>`、`[[step]]` 插值
- `useAppState` 或等价状态层：集中封装 `projects/templates/settings` 的读写动作

### 4.2 插值逻辑重复，存在规则漂移风险

[App.tsx](/E:/Project/Vscode/PromptWordSplicer/App.tsx:159) 定义了 `createInterpolator`，而 [components/ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:176) 又实现了一套近似相同的 `interpolate`。

风险：

- 未来一边改占位符规则，另一边忘记同步
- 运行态和导出态可能出现不一致

建议：

- 提取一个唯一的 `interpolateProjectText(project, template, text)` 方法
- 由 `App`、`ProjectRunner`、导出逻辑共同复用

### 4.3 Auto-resize 文本框重复实现较多

以下文件都各自维护了一套自适应 textarea：

- [components/ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:35)
- [components/TemplateEditor.tsx](/E:/Project/Vscode/PromptWordSplicer/components/TemplateEditor.tsx:31)
- [components/PromptEditor.tsx](/E:/Project/Vscode/PromptWordSplicer/components/PromptEditor.tsx:14)
- [components/Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:29)

建议：

- 抽一个共享组件，例如 `components/common/AutoResizeTextarea.tsx`
- 用参数控制只读、样式和最小高度

### 4.4 组件职责偏大，UI 与状态机混在一起

`TemplateEditor` 当前同时处理：

- 模板基础信息
- 输入变量管理
- 模型引用管理
- 步骤增删改排
- 批量选中
- 执行配置复制/粘贴
- DeepSeek 预设推荐

`ProjectRunner` 当前同时处理：

- 步骤状态推导
- 依赖分析
- 执行状态
- 日志展示
- 右侧总览
- 恢复历史输出

建议拆分子模块：

- `TemplateMetaPanel`
- `TemplateModelRefPanel`
- `TemplateStepList`
- `TemplateStepCard`
- `ProjectStepCard`
- `ProjectRunLogPanel`
- `ProjectPreviewPanel`

### 4.5 数据持久化是直接副作用写盘，缺少防抖和错误上浮

[App.tsx](/E:/Project/Vscode/PromptWordSplicer/App.tsx:327) 之后的多个 `useEffect` 会在状态变化后直接 `saveToDisk`。

问题：

- 高频编辑时会产生频繁写盘
- 保存失败只在控制台打印，不会反馈给用户
- 没有区分“脏状态”和“已落盘状态”

建议：

- 给 `projects/templates/settings` 保存增加 300ms 到 800ms 防抖
- 建一个统一的 `persistState` 层
- 保存失败时给 UI 一个轻提示，而不是只 `console.error`

### 4.6 `ioService` 类型约束偏弱

[services/ioService.ts](/E:/Project/Vscode/PromptWordSplicer/services/ioService.ts:37) 仍在大量使用 `any` 和弱校验。

问题：

- 外部导入 JSON 时，缺少 schema 级保护
- 历史数据迁移依赖上层手工兜底

建议：

- 引入运行时校验库，例如 `zod`
- 对 `settings/projects/templates` 建最小 schema
- 把“读取原始数据”和“数据迁移/校验/归一化”拆成两步

### 4.7 `modelService` 同时承担“可执行性判断”和“供应商适配”

[services/modelService.ts](/E:/Project/Vscode/PromptWordSplicer/services/modelService.ts:71) 的 `resolveStepExecutionAvailability` 和 [services/modelService.ts](/E:/Project/Vscode/PromptWordSplicer/services/modelService.ts:188) 之后的请求实现放在同一文件。

建议拆成：

- `executionAvailabilityService.ts`
- `providers/openai.ts`
- `providers/anthropic.ts`
- `providers/deepseek.ts`
- `providers/types.ts`

### 4.8 Props drilling 已经开始显著

`App.tsx` 向多个大组件传递大量回调和状态，尤其是：

- [components/FileLibrary.tsx](/E:/Project/Vscode/PromptWordSplicer/components/FileLibrary.tsx:10)
- [components/ProjectRunner.tsx](/E:/Project/Vscode/PromptWordSplicer/components/ProjectRunner.tsx:16)
- [components/Sidebar.tsx](/E:/Project/Vscode/PromptWordSplicer/components/Sidebar.tsx:14)

建议：

- 如果继续扩展功能，引入一个轻量状态层会比继续堆 props 更稳
- 可以先从 React Context + reducer 开始，不一定要马上上 Zustand

## 5. 工程层面的观察

### 5.1 Tauri 层很薄

[src-tauri/src/lib.rs](/E:/Project/Vscode/PromptWordSplicer/src-tauri/src/lib.rs:1) 只做插件注册，这意味着当前应用本质上仍是“前端应用 + 桌面容器”。

### 5.2 缺少测试与质量门

从 [package.json](/E:/Project/Vscode/PromptWordSplicer/package.json:1) 看，目前只有：

- `dev`
- `build`
- `preview`

没有看到：

- 单元测试
- 组件测试
- lint
- 独立 typecheck

建议最少补齐：

- `npm run typecheck`
- `npm run lint`
- 插值、变量同步、合并策略、执行可用性判断的纯函数测试

### 5.3 构建产物目录较大，但 Git 已做忽略

本地 `src-tauri/target` 很大，不过 [`.gitignore`](/E:/Project/Vscode/PromptWordSplicer/.gitignore:1) 已通过 `src-tauri/*` 规则整体忽略，仅放行少量配置与源码文件。

建议后续体量统计和代码扫描时继续排除该目录，避免噪音。

## 6. 优化优先级建议

### P1：近期最值得做

- 抽离统一插值服务，消除 `App.tsx` / `ProjectRunner.tsx` 重复逻辑
- 把 `App.tsx` 中的归一化、变量同步、日志拼接下沉到 domain/service
- 抽共享 `AutoResizeTextarea`

### P2：第二阶段

- 拆 `TemplateEditor` 和 `ProjectRunner` 为更稳定的子组件
- 给持久化增加防抖和失败提示
- 给导入数据增加 schema 校验

### P3：中期演进

- 引入轻量状态管理层，降低 props drilling
- 拆 provider 适配层
- 补测试与工程脚本

## 7. 是否算“大文件”

结论是：算，而且已经不止一个。

按“一个文件是否同时承载多个变化原因”来判断：

- `App.tsx`：偏大，且职责过多
- `TemplateEditor.tsx`：偏大，且功能聚合度过高
- `ProjectRunner.tsx`：偏大，且展示逻辑和运行逻辑混杂

`Sidebar.tsx`、`FileLibrary.tsx`、`SettingsModal.tsx` 目前还可接受，但继续加功能也会进入同样的问题区间。

## 8. 最终判断

这个项目当前不是“烂”，而是已经到了应当做一次结构化整理的节点。

如果现在继续直接叠功能，短期能跑，长期维护成本会明显上升。比较合理的路线是：

1. 先抽公共逻辑和纯函数
2. 再拆大组件
3. 最后再引入状态层和测试

这样改动风险最小，也最符合当前项目的成熟度阶段。
