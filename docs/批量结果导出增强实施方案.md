# PromptWordSplicer 批量结果导出增强实施方案

## 1. 目标

当前项目已经具备：

- 批量实例化
- 批量执行
- 生产节点自动化
- 结构化输出阶段 A / B

但“跑完之后如何把结果拿走继续交付”这一层还不够完整。

本方案的目标是把批量执行从“能跑完”升级成“跑完就能拿结果继续使用”，重点增强：

- 批量结果筛选
- 批量结果导出
- 结构化字段进入导出链
- 变量结果进入导出链

## 2. 适用场景

本方案优先服务以下几类使用方式：

1. 批量生成一批中间文本资产后，需要导出成表格继续整理
2. 一批项目已经完成某个步骤，需要导出该步骤结果给外部生图/生视频工具使用
3. 已经做了结构化字段拆分，希望按字段列导出，而不是只导出整段文本
4. 想快速拿到“项目名 + 关键变量 + 某步结果”的交付表

## 3. 边界

本轮只做结果导出增强，不做：

- 额外模型接入
- 生图/生视频执行
- 节点画布
- 自动重新解析结构化字段
- 导出模板市场或导出共享包

本轮只增强现有：

- 批量执行结果弹层
- 批量导出数据选择
- CSV / JSON / Markdown 导出

## 4. 设计原则

### 4.1 导出优先服务“拿结果走”

导出不是为了做系统备份，而是为了：

- 给人看
- 给表格看
- 给下游工具看

所以导出结构必须稳定、平铺、可理解。

### 4.2 结构化字段优先作为列

既然已经有结构化输出，就不应该继续只把整段文本塞进一个单元格。

优先顺序应为：

1. 项目基础信息
2. 步骤整段结果
3. 结构化字段
4. 变量值

### 4.3 不把导出做成新配置系统

第一版导出只做轻量选择，不做复杂的“导出模板编辑器”。

## 5. 导出对象分层

建议把批量导出对象分成 4 层。

### 5.1 项目基础信息

固定可选：

- `project_id`
- `project_name`
- `template_id`
- `template_name`
- `created_at`
- `last_modified_at`

### 5.2 指定步骤的整段结果

支持导出某一步的：

- `step_id`
- `step_name`
- `step_output_raw`

### 5.3 指定步骤的结构化字段

如果该步骤定义了结构化输出字段，则可展开导出：

- `step.{stepId}.field.{fieldKey}`

示例：

- `step.generate_desc.field.subject_description`
- `step.generate_desc.field.style_keywords`
- `step.generate_desc.field.negative_prompt`

### 5.4 变量结果

支持导出项目变量，至少包括：

- 输入变量
- 局部变量
- 输出变量
- 结构化输出变量

列命名建议：

- `var.{variableKey}`

## 6. 第一版导出模式

第一版建议直接支持 3 种模式。

### 6.1 导出当前批量执行结果

适用于：

- 刚跑完一批步骤
- 只想导出这次运行相关结果

内容建议默认包含：

- 项目名
- 步骤名
- 执行状态
- 整段结果
- 结构化解析状态

### 6.2 导出指定步骤结果

适用于：

- 某一步已经是“最终可复制出去”的提示词
- 想批量拿这一步的结果给外部工具用

内容建议可选：

- 整段结果
- 结构化字段
- 绑定变量

### 6.3 导出项目变量表

适用于：

- 想看一批项目当前变量状态
- 想把结构化字段同步出来的变量拿到表格里

内容建议包含：

- 项目基础信息
- 所选变量列

## 7. 导出格式

### 7.1 CSV

第一优先级格式。

优点：

- 最适合表格处理
- 最适合继续人工整理
- 最适合外部复制粘贴链路

要求：

- 列稳定
- 换行安全转义
- 空值输出为空字符串

### 7.2 JSON

第二优先级格式。

优点：

- 保留更多结构
- 适合后续程序消费

建议：

- 一条项目一条对象
- 扁平 JSON 为主
- 结构化字段作为子对象或扁平 key，首轮建议扁平 key

### 7.3 Markdown

第三优先级格式。

用途：

- 快速给人看
- 导出成报告或笔记

但第一版可以只做基础表格，不做复杂模板化渲染。

## 8. UI 方案

### 8.1 批量执行结果弹层增强

在现有批量执行结果弹层上新增：

- 导出按钮
- 导出格式选择
- 导出范围选择

范围建议支持：

- 全部结果
- 仅成功
- 仅失败
- 仅跳过
- 仅阻塞

### 8.2 步骤级导出入口

在项目页步骤区补一个轻量入口：

- `导出本步结果`

这样单项目也能快速导出某一步，不必一定从批量执行弹层走。

### 8.3 导出字段选择面板

第一版不做复杂拖拽排序，只做勾选：

- 项目基础字段
- 整段结果
- 结构化字段
- 变量字段

如果用户不选，则走默认导出集。

## 9. 默认导出集建议

为减少第一次使用门槛，建议给 3 套默认导出集。

### 9.1 文本交付版

- `project_name`
- `step_name`
- `step_output_raw`

### 9.2 结构化版

- `project_name`
- `step_name`
- 全部结构化字段列

### 9.3 变量版

- `project_name`
- 选中的变量列

## 10. 与现有结构化输出的关系

这是本方案最重要的部分。

当前阶段已经有：

- `stepOutputs`
- `stepStructuredOutputs`
- `variables`

导出增强的意义就在于把这三层结果利用起来：

1. 整段结果给人读
2. 结构化字段给流程复用
3. 变量给系统上下游衔接

所以导出层不应绕开结构化输出，而应该把它作为正式导出数据源。

## 11. 建议的实施顺序

### Phase 1：批量执行结果导出

先在现有批量执行结果弹层里补：

- `导出 CSV`
- `导出 JSON`
- 结果筛选导出

这一步最快见效。

### Phase 2：步骤结果导出

补项目页单步骤导出入口，支持：

- 整段结果导出
- 结构化字段导出

### Phase 3：变量导出增强

把结构化输出变量正式纳入变量导出范围，并支持勾选变量列。

## 12. 风险与控制

### 12.1 列过多

如果结构化字段和变量很多，CSV 会变得很宽。

控制方式：

- 第一版默认不全选所有字段
- 提供最小默认导出集

### 12.2 结果来源混淆

用户可能分不清：

- 整段结果
- 结构化字段
- 变量值

控制方式：

- 列名前缀清晰
- UI 中明确分组

### 12.3 导出格式不稳定

如果不同导出入口格式差异太大，会让后续维护困难。

控制方式：

- 统一走一个导出构建服务
- 所有入口复用同一套扁平化逻辑

## 13. 验收标准

这轮完成后，至少应满足：

1. 批量执行结果可以直接导出 CSV / JSON
2. 可以只导出成功项、失败项、跳过项等子集
3. 结构化字段能作为稳定列进入导出
4. 变量结果能进入导出
5. 用户不需要自己手工复制一条条结果到表格里
