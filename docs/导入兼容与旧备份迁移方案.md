# PromptWordSplicer 导入兼容与旧备份迁移方案

## 1. 背景

当前导入链路以“当前版本结构”作为唯一准入标准：

1. 选择文件
2. `JSON.parse`
3. `validateBackupBundle`
4. 合并或全量替换

这条链路对当前导出的备份文件有效，但对历史备份不稳定，已经出现以下问题：

1. 历史全量备份缺少当前必填运行态字段，导入在 schema 阶段直接失败
2. 历史文件可能存在 `UTF-8 / GBK / ANSI` 编码混用，JSON 虽然能读出文本，但中文内容已经乱码
3. 历史模型引用、步骤结构、变量来源定义可能与当前运行逻辑不完全一致
4. 导入失败时只有“格式错误”，用户无法知道是版本不兼容、编码异常还是引用损坏

本方案目标不是单点修一个字段，而是建立一条正式的“导入兼容流水线”，让旧备份可以被检测、迁移、校验、规范化，并产出可解释的导入报告。

## 2. 范围

本方案覆盖以下导入对象：

1. 全量备份包 `prompt_splicer_backup_*.json`
2. 旧版全量备份包，含 `version: "2.0"` 或无版本字段
3. 项目变量表 `JSON / CSV`
4. 未来可能接入的裸 `projects[]` / `templates[]` 导入

本轮不做：

1. 自动修复已经写坏且无可逆线索的乱码文本
2. 跨产品格式导入
3. 云端迁移服务

## 3. 设计原则

1. 兼容逻辑前置到校验之前，不能指望旧数据先满足当前 schema
2. 迁移与校验分层
3. 迁移只做结构补齐、字段映射、引用修复，不擅自改写业务文本
4. 所有自动兼容都要留下报告，让用户知道系统做了什么
5. 导入失败要可解释，区分编码问题、结构问题、关系问题、未知问题

## 4. 目标链路

建议把导入链路统一改造成：

1. 读取文件字节
2. 解码并探测编码
3. 解析 JSON 或变量表
4. 识别导入类型与历史版本
5. 执行版本迁移
6. 执行当前版本 schema 校验
7. 执行 normalize
8. 生成导入预览与迁移报告
9. 用户确认后再合并或覆盖

## 5. 模块拆分

建议新增以下服务：

1. `services/importEncodingService.ts`
2. `services/importDetectionService.ts`
3. `services/importMigrationService.ts`
4. `services/importCompatibilityService.ts`

建议保留现有职责：

1. `services/schemas.ts` 只负责“当前标准结构”的运行时校验
2. `domain/projectDomain.ts` 负责当前项目规范化
3. `domain/templateDomain.ts` 负责当前模板规范化
4. `components/MergeModal.tsx` 负责展示导入预览、风险提示和确认

## 6. 模块职责

### 6.1 `importEncodingService.ts`

职责：

1. 接收文件字节或文本
2. 识别编码
3. 输出文本、编码、乱码风险

建议接口：

```ts
export type ImportEncoding = 'utf-8' | 'gb18030' | 'unknown';

export interface DecodedImportText {
  text: string;
  encoding: ImportEncoding;
  warnings: string[];
  suspiciousGarbled: boolean;
}

export function decodeImportText(input: Uint8Array | string): DecodedImportText;
```

规则建议：

1. 字节流优先按 `utf-8` 解码
2. 若出现高频乱码特征，再尝试 `gb18030`
3. 若 `gb18030` 结果可读性更高，则采用 `gb18030`
4. 若只拿到字符串，至少跑乱码探测，不能静默吞掉风险

乱码探测建议关注：

1. `�`
2. 高频 `鍙 / 涓 / 鏈 / 娓 / 鐢 / 妯 / 椤`
3. 异常高比例的无意义连续 CJK 片段

### 6.2 `importDetectionService.ts`

职责：

1. 判断导入内容属于哪一类
2. 判断备份版本
3. 标记历史结构特征

建议接口：

```ts
export type ImportPayloadKind =
  | 'backup_bundle'
  | 'projects_array'
  | 'templates_array'
  | 'project_variable_table'
  | 'unknown';

export interface ImportDetectionResult {
  kind: ImportPayloadKind;
  version: string | 'legacy-unknown';
  warnings: string[];
  hints: {
    missingProjectRuntimeFields: string[];
    legacyModelPresetRefs: number;
    orphanTemplateRefs: number;
  };
}

export function detectImportPayload(raw: unknown): ImportDetectionResult;
```

判定规则建议：

1. 含 `projects` 与 `templates` 视为 `backup_bundle`
2. 纯数组且元素含 `templateId/name/inputValues` 视为 `projects_array`
3. 纯数组且元素含 `inputs/steps` 视为 `templates_array`
4. 变量表走现有变量表解析逻辑，但检测阶段仍要标出其格式类型

### 6.3 `importMigrationService.ts`

职责：

1. 执行历史版本到当前版本的结构迁移
2. 产出迁移报告

建议接口：

```ts
export interface ImportMigrationReport {
  fromVersion: string | 'legacy-unknown';
  toVersion: string;
  appliedMigrations: string[];
  warnings: string[];
  stats: {
    projectCount: number;
    templateCount: number;
    orphanProjectCount: number;
    suspiciousTextCount: number;
    patchedFieldCount: number;
  };
}

export interface ImportedBackupBundle {
  projects: unknown[];
  templates: unknown[];
  version?: string;
  exportDate?: string;
}

export interface MigratedImportBundle {
  bundle: ImportedBackupBundle;
  report: ImportMigrationReport;
}

export function migrateImportBundle(raw: unknown): MigratedImportBundle;
```

迁移形式建议：

```ts
type ImportMigration = (bundle: ImportedBackupBundle) => ImportedBackupBundle;

export const MIGRATION_PIPELINE: Array<{
  from: string | 'legacy-unknown';
  to: string;
  apply: ImportMigration;
}> = [];
```

### 6.4 `importCompatibilityService.ts`

职责：

1. 编排整个兼容导入流程
2. 作为 UI 唯一入口

建议接口：

```ts
import type { Project, Template } from '../types';

export interface PreparedImportBundle {
  projects: Project[];
  templates: Template[];
  report: ImportMigrationReport;
  detection: ImportDetectionResult;
}

export function prepareImportedBackupBundle(input: Uint8Array | string): PreparedImportBundle;
```

内部流程：

1. `decodeImportText`
2. `JSON.parse`
3. `detectImportPayload`
4. `migrateImportBundle`
5. `validateBackupBundle`
6. `normalizeTemplate`
7. `normalizeProject`

## 7. 迁移规则

### 7.1 `legacy-unknown -> 2.0`

适用于没有 `version` 的老备份。

处理规则：

1. 若有 `projects/templates`，补写 `version: "2.0"`
2. 保留原始 `exportDate`
3. 不推测新业务字段，只建立可识别的最小备份包

### 7.2 `2.0 -> 2.1`

这是当前最关键的一步。

项目级迁移：

1. `customInputs` 缺失补 `[]`
2. `stepOutputs` 缺失补 `{}`
3. `stepStructuredOutputs` 缺失补 `{}`
4. `stepOutputMeta` 缺失补 `{}`
5. `stepRunLogs` 缺失补 `{}`
6. `stepOverrides` 缺失补 `{}`
7. `variables` 缺失补 `[]`
8. `lastOpenedAt` 缺失时回落为 `lastModifiedAt || createdAt`

模板级迁移：

1. `modelRefs` 缺失补 `[]`
2. `structuredOutputFields` 缺失补 `[]`
3. `structuredOutputBindings` 缺失补 `[]`
4. `outputBinding` 缺失补空对象
5. `execution` 缺失补 `{ systemPrompt: '' }`
6. `execution.systemPrompt` 缺失补空字符串

### 7.3 历史模型引用迁移

依托 [domain/templateDomain.ts](/E:/Project/Vscode/PromptWordSplicer/domain/templateDomain.ts:12) 已有映射能力，导入时增加“报告化”：

1. 记录命中 `LEGACY_MODEL_PRESET_MAP` 的次数
2. 记录无法映射到当前 `modelCatalog` 的模型引用数量
3. 无法映射时不报错中止，但在报告中标成“需人工检查”

### 7.4 引用关系修复

项目与模板关系：

1. `project.templateId` 指向不存在模板时，标记为 orphan
2. orphan 项目允许进入预览，但默认不勾选导入
3. 用户可选择：
   - 跳过 orphan 项目
   - 强制导入为孤立项目

强制导入孤立项目的前提：

1. UI 必须明确提示“该项目导入后无法正常运行，直到绑定可用模板”

## 8. UI 交互方案

当前 [components/MergeModal.tsx](/E:/Project/Vscode/PromptWordSplicer/components/MergeModal.tsx:42) 直接选文件后进校验，建议改成“两阶段”。

### 8.1 阶段一：预解析

展示内容：

1. 文件类型：全量备份 / 项目数组 / 模板数组 / 变量表 / 未识别
2. 版本：`2.0 / 2.1 / legacy-unknown`
3. 编码：`UTF-8 / GB18030 / 未知`
4. 项目数、模板数
5. 自动迁移项数
6. 风险项数

推荐文案：

1. `检测到旧版本备份，系统将先执行兼容迁移后再导入。`
2. `检测到文件疑似使用旧版本地编码，已按 GB18030 自动解码。`
3. `发现 3 个项目缺少模板引用，默认不会加入导入队列。`

### 8.2 阶段二：确认导入

在现有队列基础上增加摘要区：

1. 已补齐字段数
2. 已迁移模型引用数
3. orphan 项目数
4. 疑似乱码字段数
5. 是否存在无法自动修复的问题

推荐文案：

1. `已自动补齐历史运行态字段，导入后将按当前版本结构保存。`
2. `部分文本疑似乱码，建议先预览后再确认导入。`
3. `部分模型引用无法映射到当前模型目录，导入后需要人工检查步骤执行配置。`

### 8.3 失败提示分级

避免统一显示“格式错误”。

建议错误分类：

1. `文件无法解析`
2. `文件结构无法识别`
3. `旧版本迁移失败`
4. `迁移后仍不满足当前数据结构`
5. `检测到严重乱码，已中止导入`

## 9. 与现有代码的衔接点

### 9.1 `ioService`

当前 [services/ioService.ts](/E:/Project/Vscode/PromptWordSplicer/services/ioService.ts:142) 直接返回文本，不利于编码兼容。

建议新增：

```ts
async selectAndReadFileBytes(): Promise<Uint8Array | null>
async selectAndReadJsonImport(): Promise<{ bytes?: Uint8Array; text?: string } | null>
```

若 Tauri 侧暂时不便读取字节：

1. 先保留文本读取
2. 在兼容服务中做字符串乱码探测
3. 后续再升级为字节流读取

### 9.2 `schemas.ts`

当前 [services/schemas.ts](/E:/Project/Vscode/PromptWordSplicer/services/schemas.ts:59) 可以继续保留部分默认值作为兜底，但不再承担“历史兼容主入口”职责。

建议原则：

1. schema 可以有轻量默认值
2. 大部分历史迁移逻辑搬到迁移层
3. schema 更偏向“当前标准结构”验证

### 9.3 `useProjectTemplateActions`

当前全量替换入口在 [hooks/useProjectTemplateActions.ts](/E:/Project/Vscode/PromptWordSplicer/hooks/useProjectTemplateActions.ts:272)。

建议：

1. `replaceImportedData` 只接收已经准备好的 `Project[] / Template[]`
2. 兼容、迁移、校验全部在进入该函数之前完成

### 9.4 `MergeModal`

建议把直接调用 `validateBackupBundle` 改成调用：

```ts
const prepared = prepareImportedBackupBundle(fileBytesOrText);
```

后续都使用 `prepared.projects`、`prepared.templates`、`prepared.report`。

## 10. 测试矩阵

建议新增 `tests/importCompatibilityService.test.ts`，至少覆盖以下场景。

### 10.1 成功场景

1. 当前版本 `2.1` 全量备份可直接导入
2. `2.0` 旧备份缺 `stepRunLogs` 可自动补齐
3. `2.0` 旧备份缺 `stepStructuredOutputs` 可自动补齐
4. 无 `version` 的历史备份可识别并迁移
5. 历史 `presetId` 可映射到当前模型目录

### 10.2 风险但可导入场景

1. orphan 项目被识别并默认不入队
2. 模型引用无法映射但导入仍成功
3. 模板步骤缺少 `execution.systemPrompt` 时自动补齐
4. 文件识别为 `gb18030` 并给出警告

### 10.3 拒绝场景

1. 不是 JSON 且不是变量表
2. 顶层结构完全无法识别
3. 迁移后仍缺核心字段如 `project.id / template.id / step.id`
4. 疑似乱码比例过高且无法确定正确编码

### 10.4 回归样本

建议落地 3 组固定样本：

1. 你当前提供的 `version: "2.0"` 旧备份裁剪样本
2. 无版本字段的最旧可识别样本
3. 带历史模型引用的样本

## 11. 分两次提交的落地顺序

### 提交一：先打通兼容主链

目标：

1. 能导入 `2.0` 和 `legacy-unknown`
2. 有迁移报告
3. 不改太多 UI 结构

变更范围：

1. 新增 `importDetectionService.ts`
2. 新增 `importMigrationService.ts`
3. 新增 `importCompatibilityService.ts`
4. `MergeModal` 接入新入口
5. 补核心测试

验收标准：

1. 旧备份能进预览而不是直接失败
2. 用户能看到“已自动补齐字段”的说明
3. 现有新备份导入行为不回退

### 提交二：再补编码与风险展示

目标：

1. 解决乱码识别
2. 让导入报告更完整
3. 让 orphan 风险更可见

变更范围：

1. 新增 `importEncodingService.ts`
2. `ioService` 增加字节读取接口或兼容层
3. `MergeModal` 增加编码/风险摘要区
4. 补编码测试

验收标准：

1. 可识别典型 `UTF-8 / GB18030` 旧文件
2. 疑似乱码不会静默导入
3. orphan 项目和模型映射风险可见

## 12. 推荐最小实现

如果当前只想先解决真实使用问题，建议按以下最小闭环落地：

1. 引入 `prepareImportedBackupBundle`
2. 支持 `legacy-unknown` 与 `2.0 -> 2.1` 迁移
3. 把 `MergeModal` 改成先显示导入报告
4. 增加旧备份回归测试
5. 第二轮再补编码识别

这样可以先把“导入旧提示词库失败”从阻断问题降级为“可导入但带风险提示”的可控问题。
